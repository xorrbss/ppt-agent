### One transient import failure, not from today's commits

Between roughly 03:13 and 03:16:40 the shared worktree did not import:

    ImportError: cannot import name 'is_authored_publish_flagged_slides_enabled'
    from 'utils.get_env'

reached through `services.workspace_operation_worker` →
`account_deletion_controller` → `workspace_cleanup_journal_service` →
`authored_checkpoint_service` → `authored_checkpoint_state` →
`authored_admission_checkpoint` → `authored_admission_session` →
`authored_terminal_slide_policy`.

This was **not** a defect in the committed code. Commit `f6db6f33d` carries the
re-export in `utils/get_env.py`; the break existed only in an uncommitted
intermediate state, written at 03:09:56 by a concurrent session working in the
same worktree, and removed again by 03:16:40. It is recorded here because it is
a live hazard of the shared tree, not because the export lane is broken: the
api and both controllers had already imported the chain at 02:59:47, before the
edit landed, and a re-check at 03:19:34 found
`services.workspace_operation_worker`, `services.public_export_operation`,
`services.presentation_export_direct_attempt_service` and
`services.authored_presentation_generation` all importing cleanly.

HEAD advanced twice during this session (f6db6f33d → 706b59e5c → 4848dcbb7)
with ~40 files still dirty on top. The two exports below therefore ran against
worker processes that loaded **f6db6f33d** at boot.

Two consequences for how this row should be read:

- It is a genuine pass of the **reuse** path on the new code, including
  `f87269c6d` which binds the export identity to the worker bundle it runs: the
  identity still matched, so the reuse survived that change.
- It is **not** a measurement of the Hybrid render/assemble lane, and the
  −867 s wall delta is a cache hit, not a speed-up. `slideFallbacks` and
  `qualityStatus` come back `null` rather than `[]` because a reused artifact
  carries no fresh worker quality receipt — so the "slideFallbacks empty"
  acceptance cannot be evaluated from this run at all. The acceptance line
  `slideFallbacksEmpty: false` in `52-evidence.json` means *absent*, not
  *non-empty*.

There is no sanctioned way to force a rebuild from the workspace command: the
context accepts only `format`, `pptx_mode` and `font_embedding`, and the
identity is content-addressed over the deck, the export mode, the render
adapter, the exporter version and the evidence digests. Re-measuring the lane
on this deck needs a deck or exporter change, neither of which was in scope.

**All 28 fallbacks carry one code: `chrome-teardown-timeout`.** The quality
summary reads `editableSlides: 7`, `imageFallbackSlides: 28`,

Two things make this worth acting on rather than filing as deck variance:

- `mapHybridSlideFallbackCode` in
  `servers/nextjs/scripts/lib/hybrid-slide-fallback-code.mjs` classifies this
  code ahead of the generic timeout rule precisely because, in its own words,
  "a cleanup helper that ran out of time did not fail the measurement it
  followed". The measurement succeeded; the Windows Chrome cleanup helper then
  timed out, and the slide was rastered anyway. Twenty-eight slides lost their
  native layer to a step that runs *after* the work that produced it.
- The time did not go into rendering or assembly. `renderWallMillis` is 68,392
  and `artifactStageMillis` 31,219, but `exportSchedulerQueueWaitMillis` is
  **833,235 of the 834,126 worker milliseconds — 99.9 % queue wait**. The six
  dispatches are 14.8 s, 2.9 s, 12.3 s, 3.6 s, 11.4 s and 831.6 s; only the last
  is long, and it is almost entirely waiting.

`slidesNotAttempted` is 0 against a `deckBudgetMillis` of 1,495,562, so
`353821dd4` did its job: nothing was started that the budget could not finish.
`4dc9ebaa2` also did its job — the per-slide fallback evidence is durable in the
receipt, which is how this is visible at all.

### Confound that must not be dropped

Throughout this window a second session was working in the same worktree on the
same Windows host, editing ~40 files and exercising its own suites (the
transient import failure in §1 is that session's footprint). `chrome-teardown-timeout`
originates in a Windows process-table scan-and-kill helper, and 833 s of export
scheduler queue wait is the signature of a contended host. This run therefore
establishes that the failure mode reproduces on the current code under load; it
does **not** establish that today's commits caused it, and the two decks are not
the same deck. A quiet-host repeat of run-21 is the next measurement, and it is
the one that would separate `0047ca57f` (share the Windows cleanup scan and
queue its helpers) working from it being overwhelmed.
