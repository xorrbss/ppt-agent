# 원문 보존 구조 보정 v3 설계

작성일: 2026-09-10

상태: 사용자 승인 방향에 따른 구현 설계. 이 문서는 구현 완료나 실제 문서 성공 증거가 아니다. 아래 예산과 인터페이스는 구현 시 확인할 제안이다.

검토 반영: 결함 원인에 따른 후보 우선순위, 공통 예산 배분, 순차 실행의 선택 규칙, 개선 및 디자인 보호의 측정 기준을 구체화했다. 수치 임계값은 검증 전 정책 제안이며 제품 성능이나 통과율을 뜻하지 않는다.

기존 [v2 설계](authored-structural-quality-repair-design-20260910.md)의 원문 보존, 엄격한 최종 승인, 체크포인트 fencing 계약을 유지한다. 범위 계산, 후보 평가의 상태 관리, 후보 탐색과 예산에 대해서는 이 문서를 우선한다. v2의 구현·검증 기록은 당시 이력으로 보존한다.

## 1. 목표와 완료 경계

잘리지 않은 DOM으로 수정 범위를 계산하고, 작은 구조 후보를 기존 보정 경로에서 측정한다. 모든 후보는 동일한 기준 상태에서 평가하며 선택된 하나만 다음 상태가 된다. LLM은 결정론적 후보로 해결되지 않은 결함에 제한된 패치를 제안한다.

- 원문 텍스트·블록 ID·QID·DOM 순서·자산 계약을 유지한다.
- 9.5pt 및 더 엄격한 기존 역할별 하한을 유지한다. 실제 측정의 px/pt 변환과 배율을 명시한다.
- 텍스트 축약, 노드 추가·삭제, 이미지 교체, 내용 숨김, 자유로운 HTML 재작성은 허용하지 않는다.
- 중간 개선은 메모리의 작업 상태이며 게시·완료 체크포인트가 아니다.
- 슬라이드 최종 승인은 같은 HTML·PNG·metrics의 composition과 strict source readback 통과로 판정한다.
- 네 장 통과와 전체 35장 완료는 별개의 증거다. 각 장은 해당 원문 계약, 전체 실행은 289/289를 확인한다.
- 제한 탐색 실패는 배치 불가능의 증명이 아니다. 성공을 보장하거나 실측 전 속도·품질 점수를 부여하지 않는다.

## 2. 실제 재현에서 확인한 시작점

기존 체크포인트 네 장을 다시 캡처한 검증에서 전부 `repair_scope_unavailable`로 중단됐다. 이 검증의 모델 호출은 0회다.

| --- | --- | --- |
| 22 | 프롬프트 축약으로 DOM 61개 중 6개 누락 | 원문 읽기가 이미 정상이어도 카드 배치만 개선된 중간 후보 허용 |

## 3. 처리 흐름과 데이터 경계

```text
원본 HTML + manifest + outline + 완전한 브라우저 측정
  → 원본 기준 고정 / 전체 DOM 그래프 구성
  → 결함의 원인·영향 관계로 보정 그룹 선정
  → 현재 상태에서 결정론적 후보 생성
  → 공통 기준으로 후보 측정·평가 → 하나 선택
  → 최종 통과면 증거 결합·저장
  → 부분 개선이면 선택 상태에서 범위 재계산
  → 필요 시 관련 DOM만 담은 LLM 패치 제안
  → 같은 평가·선택 경로 → 통과 또는 예산 종료
```

세 데이터를 구분한다.

| 객체 | 역할 | 제한 |
| --- | --- | --- |
| FullDomGraph | 전체 QID, 부모 관계, 실제 레이아웃/clip 관계, 측정값 | 프롬프트 글자 제한을 적용하지 않음. 수집 불완전성은 명시적 오류 |
| RepairScope | editable, affected, protected와 관련 원문 계약 | 수정 권한과 영향 범위를 분리; 편집 action 수와 DOM 노드 수를 혼동하지 않음 |
| PromptDom | 해당 후보 제안에 필요한 구조·측정 요약 | 기본 48,000자 예산 유지; 전체 DOM 분석 후 구성 |

FullDomGraph는 LLM용 문자열로 직렬화하기 전에 구성한다. `compact_dom_map_for_prompt`를 scope 계산에 호출하지 않는다. 실제 DOM은 유한 자원이므로 기존 캡처 상한과 그래프 순회 보호는 유지한다. 안전 상한에 걸리면 잘린 결과를 완전한 그래프로 취급하지 않는다.

## 4. 보정 범위 선정

1. 원문 결함 대상뿐 아니라 실제 clipping ancestor, 가리는 요소, containing block을 찾아 원인 관계를 구성한다.
2. DOM 부모와 CSS 배치 소유자를 구분한다. 중간에 QID 없는 wrapper가 있으면 원래 관계를 수집하고 가장 가까운 QID 조상과 연결하되 wrapper 제약을 보존한다.
3. grid/flex뿐 아니라 실제 크기를 제한하는 일반 block 컨테이너도 후보가 될 수 있다. 공통 조상이라는 이유만으로 수정 권한을 부여하지 않는다.
4. 독립된 결함은 별도 그룹으로 다룬다. 부모 reflow, 겹침, clip 또는 공유 공간 제약으로 연결된 그룹은 합친다. 서로 영향을 주는 패치를 독립 후보로 적용하지 않는다.
5. 그룹을 선택할 때 수정 가능한 QID, 간접 이동 가능한 전체 하위 요소, 범위 밖 보호 요소를 계산한다. 형제와 외부 가림 요소도 경계 정보에 포함한다.
6. 선택 상태가 바뀌면 그래프와 그룹을 재계산한다. 원본 대비 누적 변화 검사는 계속 유지한다.

### 최상위 콘텐츠 컨테이너

`parent=null`만으로 허용 또는 거부하지 않는다. 실제 HTML/브라우저 관계에서 부모 없는 이유를 확인한다. `html`, `body`, 캡처 프레임, 슬라이드 캔버스와 콘텐츠 컨테이너를 구분한다. 유효한 QID, 자식, 관련 원문, 콘텐츠 역할 또는 확인 가능한 배치 근거를 요구한다.

시스템 루트는 읽기 전용이다. 명시적 콘텐츠 컨테이너만 제한된 구조 속성을 수정할 수 있다. 부모 정보가 빠진 경우에는 동일 capture에서 추가 수집을 우선하며, 새 capture가 필요하면 예산에 포함한다. 추측으로 루트 보호를 해제하지 않는다.

기존 editable QID 16개 상한을 피하려고 자식을 생략하지 않는다. 소유자만 직접 수정해도 되는 경우 자식은 affected로 보존한다. 실제로 16개 초과 직접 편집이 필요하면 독립 분할 가능성을 확인하고, 불가능하면 명시적으로 종료한다.

## 5. 프롬프트 구성

선택된 그룹의 owner, 직접 자식 전체, 결함 원인 경로, 영향 받는 원문 요약, 외부 보호 경계를 담는다. 정확한 원문은 서버에서 보존·검증한다. 모델이 읽는 요약을 원문 검증 기준으로 사용하지 않는다.

예산을 넘으면 긴 텍스트 요약, 불필요한 스타일 제거, 상속 스타일 중복 제거 순으로 축약한다. QID·관계·핵심 치수·원인 정보는 유지한다. 읽기 전용 하위 트리를 요약할 때도 구성원 ID와 범위를 명시하며 편집 대상으로 노출하지 않는다.

독립 그룹으로 분할할 수 없고 필요한 구조 정보가 여전히 예산을 초과하면 `repair_prompt_budget_exceeded`로 종료한다. 입력 뒷부분을 잘라서 보내지 않는다. 이미지와 지시문도 모델 입력에 포함되므로 48,000자 제한을 모델 토큰 한도의 보장으로 간주하지 않는다.

## 6. 후보 평가와 선택

기존 `make_source_repair_evaluator`는 평가 중 previous 상태를 변경한다. 이를 평가와 상태 전진으로 분리한다. 아래는 개념 인터페이스이며 기존 모듈 내에서 확장한다.

```text
evaluate(original, selected, candidate, scope, policy) -> Assessment
select(selected, assessments) -> Candidate | None
advance(expected_selected_digest, winner) -> new_selected
```

- evaluate는 입력을 변경하지 않는다. 같은 입력의 결과는 후보 평가 순서와 무관하다.
- 한 비교 집합의 후보는 동일한 selected digest에서 생성·평가한다.
- 초기 구현에서는 후보를 고정 우선순위로 하나씩 평가한다. reject이면 같은 selected에서 다음 후보를 시도하고, provisional이면 즉시 하나만 advance한 뒤 남은 이전 기준 후보를 폐기·재계산한다. admitted이면 종료한다.
- 다른 기준 상태에서 생성된 후보는 새 selected 위에 재사용하거나 패치를 겹쳐 적용하지 않는다.
- 캐시 키에 원본/selected/candidate HTML digest, metrics digest, scope·정책·원문 계약 버전을 포함한다.
- 동률은 변경 비용, 후보의 고정 순번, digest 순으로 결정한다. 처리 완료 순서로 선택하지 않는다.

향후 동일 selected의 후보들을 병렬 평가한다면 고정 우선순위 접두부가 판정된 뒤 첫 admitted를 선택한다. 낮은 우선순위 후보가 먼저 통과해도 앞선 후보의 판정 전에는 선택하지 않는다. admitted가 없으면 비교 집합 평가가 끝난 뒤 provisional 중 하나를 선택한다. 취소한 실행의 비용도 계상한다. 이 병렬 경로는 초기 구현 범위에 포함하지 않는다.

### 필수 조건과 개선 조건

원문 무결성·순서·QID·허용 action·폰트 하한·역할/자산 계약·보호 영역·측정 완전성은 점수로 상쇄할 수 없는 조건이다. 신규 원문 가시성 실패나 신규 blocking 결함도 거절한다.

원본부터 clipping/occlusion이 존재하는 경우 그 자체로 모든 중간 후보를 거절하지 않는다. 블록별 가시성은 original과 selected 대비 악화되지 않아야 한다. 기존 geometry 허용 오차를 적용하며 누락된 측정값을 0으로 치환하지 않는다.

중간 후보는 위 조건을 지키면서 다음 중 하나가 명확히 개선되면 provisional이다.

- 원문 블록의 clipping/occlusion/이탈이 감소한다.
- 원문 가시성은 유지되고 composition 결함의 수 또는 연속 측정량이 감소한다.

결함은 배열 위치가 아닌 category·원인 QID·대상 QID·source ID로 대응시킨다. 결함 수 감소가 다른 블록의 악화를 가리지 않게 개별 대응을 먼저 검사한다. 픽셀 거리와 면적 비율을 단위 없이 합산하지 않는다.

필수 조건을 통과한 후보의 우선순위는 최종 통과 여부, blocking 결함 수, 유형별 정규화된 잔여 결함, 변경 비용 순이다. 단일 가중 합산 점수로 승인 여부를 결정하지 않는다. 최종 통과 후 더 예쁜 후보를 찾기 위한 추가 탐색은 하지 않는다.

### 개선 판정의 측정 기준

허용 오차와 탐색을 계속할 만큼의 개선량을 구분한다. 아래 기준은 provisional 선택에만 적용한다. 최종 strict gate를 모두 통과한 후보는 이 최소 개선량에 못 미쳐도 admitted다.

| 측정 | 비악화 판정 | 명확한 개선의 초기 제안 |
| --- | --- | --- |
| 원문 무결성·신규 가시성 실패·신규 blocking | 허용 오차로 면제하지 않음 | 해당 실패가 실제로 해소되고 다른 필수 조건을 유지 |
| viewport/card 이탈 거리 | original과 selected 각각 대비 기존 `GEOMETRY_TOLERANCE_PX` 이내 | selected 대비 감소량이 `max(2 × 허용 오차, 잔여 거리의 5%)` 이상 |
| clipping/occlusion 비율 | 기존 검증기의 허용 오차 유지; 정의가 없으면 증가 불허 | selected 대비 `max(0.01, 잔여 비율의 5%)` 이상 감소. 0.01은 1%p |
| composition blocking 수 | 결함별 대응 검사 후 신규 결함 및 기존 결함 악화 불허 | 같은 gate 기준으로 대응 결함 하나 이상 해소 |

다른 composition 연속 측정량은 단위와 허용 오차를 기존 검사에 연결한 경우에만 개선 근거로 사용한다. 기준이 없는 측정값은 receipt에 남기되 임의 점수로 provisional을 승인하지 않는다. 작은 잔여 결함이 정상 임계값 아래로 내려가면 결함 해소로 판정할 수 있다.

거리·비율 감소량은 원문 블록 또는 결함별로 계산한다. 서로 다른 블록의 합계 개선으로 개별 악화를 상쇄하지 않는다. 캡처의 viewport·폰트 준비 상태·자산·측정 버전이 다르면 먼저 증거 호환성을 확인한다. 수치 조정은 정책 버전 변경으로 관리하며 테스트 통과를 위해 임의 완화하지 않는다.

### 디자인 보호 기준의 연결

| 보호 항목 | 기준 출처와 판정 |
| --- | --- |
| 글꼴·제목/본문 관계 | 기존 역할별 정책과 9.5pt 중 엄격한 하한 적용. 제목/본문 계층 역전 금지 |
| 색상·장식·이미지 | 기존 스타일 계약 및 원본 computed style, 이미지 비율/자산 계약 유지 |
| 카드 최소 폭·간격 | 기존 style/role 계약에 명시된 하한을 사용. 원본 카드 폭 자체를 최소 폭으로 오인하지 않음 |
| 시각적 읽기 순서 | manifest/outline의 그룹·순서 및 스타일의 행/열 읽기 규칙을 bbox에 대응. `order`, 역방향 배치, 의미 그룹 분리로 순서가 바뀌면 거절 |
| 카드 정렬·반복 규칙 | 같은 반복 그룹의 기존 정렬과 간격 규칙 적용. 원래 다른 디자인의 카드를 억지로 동일화하지 않음 |

폭 하한이나 읽기 규칙이 없는 경우, 코드·모델이 제안한 열 변경에 공통으로 같은 제한을 적용한다. 실제 줄바꿈·원문 가시성은 측정하되 그것만으로 디자인 적합성을 인정하지 않는다. 필요한 기존 계약을 확보하지 못하면 해당 열 변경 후보는 제외하고 `repair_design_constraint_unavailable` 상세 사유를 남긴다. 정확히 같은 열 수·읽기 구조를 유지하는 안전한 조정 가능성은 별도로 확인한다.

### 보호 측정의 누락

보호 요소의 bbox가 없거나 0인 경우 실제 이동과 구분한다. 원문/가시 요소의 증거 누락은 `repair_measurement_incomplete`로 처리한다. 비렌더링 노드는 명시적 상태로 표현하며 임의로 geometry 통과시키지 않는다. HTML·스타일 무결성은 별도로 검사한다.

## 7. 제한된 후보 생성과 비용

기존 `_deterministic_repair_candidate`와 containment 경로를 확장한다. 별도 범용 레이아웃 엔진은 도입하지 않는다. 원자 패치 적용과 후보 capture도 기존 경로를 재사용한다.

후보 우선순위는 확인된 결함 원인과 현재 제약에서 회수 가능한 공간으로 결정한다. 기존 role/style 계약의 최소 간격·폭·글꼴 제약을 적용한다. 카드 최소 폭이나 읽기 순서 계약이 불명확하면 열 변경을 안전한 후보로 단정하지 않는다.

### 원인별 후보 선택

| 상황 | 첫 후보 | 다음 단계 |
| --- | --- | --- |
| 간격·padding의 허용 감소만으로 필요한 공간을 확보할 수 있음 | 해당 owner의 간격·padding을 묶은 최소 변경 | 실제 capture에서 남은 원인을 다시 측정 |
| 허용되는 간격 조정으로도 잔여 이탈을 해소할 수 없음 | 적용 가능한 grid/flex/카드 크기의 구조 변경 | 열 변경이 필요하면 폭·읽기 순서 계약부터 확인 |
| overlap의 원인이 position/containing block/공유 영역임 | 해당 원인을 함께 수정하는 지원 패턴 | 원인을 설명할 수 없으면 간격 후보를 소모하지 않고 LLM 제안 |
| clipping 주체나 부모 관계가 불명확함 | 측정 보완과 scope 재구성 | 측정이 부족한 채 후보 생성하지 않음 |

고정 행 수 r에서 회수 가능한 세로 공간은 `(r-1) × 허용 row-gap 감소 + 허용 상하 padding 감소`로 산출할 수 있다. 이것이 필요한 공간보다 작으면 간격 조정만으로 해결되는 후보는 생략한다. 이 계산은 원인이 일치하고 행 수·폭·내용 높이가 유지되는 경우에만 적용한다. 줄바꿈, margin collapse, absolute positioning 등으로 전제가 깨지면 회수량을 미확정으로 표시한다.

사전 계산은 후보를 제외하거나 우선순위를 정하는 근거이며 최종 통과 증거는 아니다. 후보마다 대상 결함, 변경 속성, 예상 회수 공간, 계산 전제, 패턴 ID를 기록한다. 28장의 11px와 34장의 큰 이탈을 같은 순서로 처리하지 않는다.

34장의 열 수 변경 후보는 카드 폭과 줄바꿈 후 실제 높이를 함께 측정한다. `grid-template-rows` 등 patch engine이 지원하지 않는 속성은 지원을 확인하기 전 제안 목록에 넣지 않는다. 현재 허용 목록과 프롬프트 능력을 일치시킨다.

초기 비용 제안은 슬라이드당 새 후보 capture 총 3회, 실제 provider 전송 최대 2회다. v2의 기존 상한 안에서 결정론적 후보와 모델 후보가 같은 capture 예산을 나눈다. 기존 durable 한도가 더 작으면 작은 값을 따른다.

예산 배분은 아래 규칙을 적용한다. 모델 경로가 허용되고 해결되지 않은 결함이 있으면 최소 1회의 후보 capture를 모델용으로 남긴다. 후보 조합의 Cartesian product를 만들지 않는다. 독립 그룹 수만큼 예산을 새로 부여하지 않는다.

| 상태 | 배분 규칙 |
| --- | --- |
| 원인에 맞는 지원 패턴이 있음 | 결정론적 후보 1회를 우선 실행. 남은 2회는 기본적으로 모델 후보에 배정 |
| 첫 결정론적 후보가 provisional이고 남은 원인에 별도 지원 패턴이 있음 | 두 번째 결정론적 후보를 허용하고 마지막 capture 1회는 모델용으로 예약 |
| 첫 결정론적 후보가 reject 또는 개선 없음 | 같은 패턴의 숫자만 바꾸며 반복하지 않고 모델로 전환 |
| 처음부터 적용 가능한 패턴이 없음 | 결정론적 후보를 생략하고 모델 제안 최대 2회. 남은 capture를 사용하기 위한 추가 호출은 하지 않음 |
| 모델 사용 불가/전송 예산 소진 | 근거가 있는 결정론적 후보만 남은 총 capture 예산 안에서 실행 |
| admitted 또는 deadline/공통 예산 소진 | 즉시 종료. 독립 그룹이나 재시작에서 새 예산을 만들지 않음 |

새 후보는 허용 action, 중복 digest, 원문 변경, 디자인 제약을 capture 전에 검사한다. 사전 거절은 capture를 소비하지 않지만 provider 전송이 이미 있었다면 전송 예산은 소비한다. 모델 호출 전에는 후보 capture 슬롯과 남은 deadline을 확인한다. 실행을 시작한 실패·취소 capture도 차감한다. 기준 재수집 실패 후 남은 예산으로 불완전한 측정을 우회하지 않는다.

기준 evidence가 유효하면 capture를 재사용한다. 기준 재수집은 최대 1회로 별도 계상하며, 추가 capture/실패/취소도 실제 비용에 기록한다. 시간 제한은 기존 작업의 남은 deadline을 상한으로 사용한다. 프로세스 재시작으로 예산이 복원되지 않는다.

초기 구현은 슬라이드 내부 후보를 순차 생성·평가하는 방식으로 확정한다. 다른 슬라이드는 기존 스케줄러와 렌더 제한 안에서 병렬 처리할 수 있다. 후보 간 병렬 렌더는 이번 구현에서 제외하며, 이후 필요성이 측정되면 6절의 고정 우선순위 선택 계약을 따른다. 기존 렌더 제한을 공유하며 새로운 중첩 worker pool을 만들지 않는다.

LLM에는 관련 구조, 결함 측정, 실패한 후보와 이유, 허용 action을 제공한다. 실제 적용 가능한 패치를 반환하게 하고 코드가 검증한다. 자유로운 전략 텍스트를 실행 계획으로 추측하지 않는다.

## 8. 저장·재개·실패 처리

admitted인 정확한 HTML·PNG·metrics와 평가 증거만 기존 저장 경계로 전달한다. existing repair claim, attempt fencing, 절대 슬라이드 인덱스, digest 결합과 원자적 게시 기준을 유지한다. 평가 정책을 변경하므로 gate version과 재개 호환성 처리를 명시적으로 갱신한다. 이전 영수증이 새 계약을 입증하지 못하면 재검증하며 무조건 재사용하지 않는다.

scope는 현재 selected 기준으로 재계산해도 전체 변경의 허용 범위를 확대하는 수단으로 쓰지 않는다. 원본 대비 역할·원문·보호 계약 검사를 최종 저장 전 다시 적용한다.

기존 `repair_scope_unavailable`의 상세 사유로 graph 불완전, owner 없음, 보호 경계 충돌, action 예산 초과를 구분한다. 추가로 prompt 초과, 측정 누락, 개선 없음, 검색 예산 종료를 기록한다. 가능하면 기존 오류 envelope의 detail을 확장하며 공개 API 코드를 불필요하게 변경하지 않는다.

재현 receipt에는 baseline/selected/candidate digest, 절대 인덱스, 그룹, 모델·reasoning 설정, 실제 전송 수, 렌더 수, 대기·capture·평가 시간, 결정 사유와 남은 예산을 기록한다. 설정 모델과 실제 호출 여부는 분리한다.

후보 선택 근거로 pattern ID, 예측 공간과 전제, 생략 사유, 모델용 예약 capture 수를 추가한다. provisional에는 결함별 before/after, 적용 허용 오차와 최소 개선량, 디자인 계약 출처/버전을 남긴다. 원문 내용이나 비밀 설정을 receipt에 중복 기록하지 않는다.

## 10. 검증 계획과 성공 판정

설계 단계에서는 문서 내용만 확인한다. 구현 후에는 변경 계층의 가장 좁은 기존 검사를 선택한다. 필요한 계약 검증은 다음과 같으며 전체 테스트를 기본 실행하지 않는다.

- 48,000자를 넘는 전체 DOM의 결함 QID가 scope에서 보존된다.
- 콘텐츠 컨테이너와 실제 시스템 루트/누락 부모가 구분된다.
- 같은 후보 집합의 평가 순서를 바꿔도 결과와 selected가 동일하다.
- 원문이 정상인 상태에서 composition만 개선된 후보가 provisional이 된다.
- 다른 결함이 줄어도 새 원문 손상·보호 영역 변경은 거절된다.
- 이전 selected에 대한 캐시/후보가 새 selected에 잘못 적용되지 않는다.
- 후보 및 provider 예산, 임시 후보 저장 차단, 절대 인덱스와 재개 증거가 유지된다.
- 간격으로 확보 가능한 공간이 부족한 결함에 간격 전용 후보 capture를 소모하지 않는다.
- 첫 결정론적 후보 reject 후 모델 전환, provisional 후 두 번째 패턴의 허용 조건, 모델용 마지막 capture 예약이 일관된다.
- 오차 이내 변화는 개선으로 인정하지 않으며 실제 최종 통과는 최소 개선량 조건으로 거절하지 않는다.
- 폭/읽기 규칙이 없는 열 변경은 코드·모델 후보 모두 같은 기준으로 제외된다.
- 초기 구현에서 슬라이드 내부 후보는 순차 실행되며 provisional 선택 후 이전 기준 후보가 재사용되지 않는다.

그 다음 동일 원본·옵션·체크포인트의 22/28/30/34장만 실제 보정한다. 각 장의 composition blocking residual 0, 해당 원문 readback 전부 통과, 글꼴/보호 계약 통과를 요구한다. 단순 scope 생성이나 모델 응답을 성공으로 기록하지 않는다.

네 장이 모두 통과한 뒤 동일 원본 bytes·옵션의 새 자산/스냅샷으로 전체 35장 실행 1회를 진행한다. 서로 다른 실행의 성공 지표를 합치지 않는다. 목표 증거는 한 실행의 attempt 1, operation retry 0, 35/35, 원문 289/289, quality residual 0, published, 실제 PPTX artifact다.

PostgreSQL managed stack을 사용하며 `AUTHORED_SLIDE_RENDER_CONCURRENCY=2`를 실제 generation worker 경로에서 확인한다. 배치 5·클러스터 2·렌더 2의 effective 값과 제한 적용 범위를 기록한다. 환경변수 이름이 비슷하다는 이유로 같은 제약으로 간주하지 않는다.

현재 설계의 성공 가능성은 네 장의 실제 통과로 판단하며, 속도 개선은 같은 입력의 보정 시간·실제 호출·capture 비용으로 판단한다. 반복 실행에 의한 성능 측정은 별도 요청 없이 확대하지 않는다.
