# 최대 수정 단일 모드 설계

- 작성일: 2026-08-12
- 상태: 설계 확정
- 대상: AI 작성 프레젠테이션 `quality.review`

## 1. 결정

품질검수는 별도의 안전 수정/최대 수정 선택지를 제공하지 않는다. 기존
`analyze_and_fix` 요청은 항상 **최대 수정 단일 모드**로 실행한다. 사용자에게는
하나의 동작만 보이지만 내부에서는 패턴 수정, 개별 규칙 수정, LLM 수정계획의
3단계 경로를 사용한다.

최대 수정은 콘텐츠를 새로 쓰는 기능이 아니다. 텍스트, 숫자, 중요 토큰,
이미지, 콘텐츠 계층과 읽기 순서를 보존한 상태에서 레이아웃 연산을 최대한
탐색한다.

품질검수는 미해결 페이지를 자동으로 재생성하지 않는다. `페이지 다시 만들기`는
없애지 않고, 미해결 결과를 확인한 사용자가 별도로 선택하는 기존 단일 페이지
기능으로 유지한다. LLM은 자동 수정 경로에서 페이지를 생성하지 않고 제한된
형식의 레이아웃 `RepairPlan`만 제안한다.

## 2. 목표와 비회귀 조건

우선순위는 다음과 같다.

1. 확인된 물리적 문제를 가장 많이 해결한다.
2. 새 hard violation, 콘텐츠 손실 또는 OCR 중요 토큰 손실을 만들지 않는다.
3. 같은 구조와 원인의 문제는 패턴 레시피로 묶어 중복 탐색과 렌더링을 줄인다.
4. 한 슬라이드의 충돌 없는 수정은 하나의 복합 계획으로 병합한다.
5. 후보 하나가 실패하면 검증된 차선 후보를 필요한 만큼 순차 시도한다.
6. 패턴 수정이 맞지 않는 슬라이드는 기존 개별 정밀 수정 경로로 복귀한다.
7. 설명 없는 미해결을 만들지 않는다.

속도 최적화가 기존 품질을 낮추지 않도록 다음 조건을 고정한다.

- 패턴 레시피는 확정 변경이 아니라 후보로만 사용한다.
- 모든 슬라이드는 독립적으로 최종 전체 렌더링과 품질 검증을 통과해야 한다.
- 저비용 검사는 후보 제거와 우선순위 결정에만 사용한다.
- 품질이 이전 상태보다 나빠진 수정은 게시하지 않거나 롤백한다.
- 분석과 렌더링은 제한적으로 병렬화하지만 최종 파일 게시에는 슬라이드별 잠금을 사용한다.
- 캐시는 슬라이드 리비전과 콘텐츠·스펙 해시가 일치할 때만 사용한다.

자동 수정 성공은 schema/invariant, source projection round-trip, DOM, constraint,
Chrome render, OCR, VQA, CAS publish, active read-back과 post-verify를 모두 통과한
경우에만 인정한다.

## 3. 전체 실행 구조

```text
전체 슬라이드 1회 고속 사전 검사
  → 물리적 이슈와 구조 fingerprint 생성
  → 재사용 가능한 strict pattern cluster 구성
  → 패턴별 2~3개 대표 표본 선정
  → 대표 표본에서 매개변수형 수정 recipe 생성·검증
  → 각 슬라이드에 recipe를 구조적으로 재결합하고 값 자동 보정
  → 같은 슬라이드의 충돌 없는 연산을 composite RepairPlan으로 병합
  → 저비용 게이트부터 후보를 지연 검증
  → 필요한 후보만 렌더링하고 슬라이드별 최종 전체 검증
      → 성공: 슬라이드별 게시, recipe와 사용 실적 기록
      → 실패: 개별 deterministic 정밀 수정 경로
      → 계속 실패: bounded LLM RepairPlan 경로
  → 적용 후 남은 이슈만 다시 검사
  → 미해결 결과와 구체적인 reason 반환
```

### 3.1 내부 3단계 경로

1. **패턴 경로**: 이미 검증된 레시피를 구조가 같은 슬라이드에 재사용한다.
2. **개별 규칙 경로**: 패턴이 없거나 재사용에 실패한 슬라이드를 기존 규칙과
   제약 해법으로 처리한다.
3. **LLM 수정계획 경로**: 앞의 두 경로가 실패한 문제에만 닫힌 형식의
   `RepairPlan`을 요청한다. 동일 패턴에는 가능한 한 패턴당 한 번만 호출한다.

사용자는 이 경로를 선택하지 않는다. 모두 최대 수정 단일 모드 내부의 구현이다.

## 4. 패턴 군집과 대표 표본

이슈 코드만 같다는 이유로 같은 패턴으로 취급하지 않는다. 패턴 키에는 다음을
포함한다.

- 결함 코드와 심각도
- 대상 layout tree 경로와 구조 shape
- 대상·부모 layout primitive
- content kind와 텍스트 밀도 구간
- imported HTML의 tag, display, position, overflow
- text-fit 정책
- 인접 요소와 constraint footprint
- 허용된 mutation envelope

재사용 대상이 1장뿐이면 패턴 경로를 생략한다. 같은 패턴이 여러 장이면 텍스트
밀도와 사용 가능한 공간을 기준으로 낮음·중간·높음에 해당하는 최대 3개 표본을
선정한다. 첫 번째 슬라이드를 무조건 대표로 사용하지 않는다.

대표 표본 중 하나에서만 성공한 절대 좌표 수정은 공통 레시피로 승격하지 않는다.
표본 전체에서 동일한 구조 규칙이 성립하거나, 슬라이드별 보정 후 모두 검증을
통과해야 재사용 가능한 레시피로 등록한다.

## 5. 매개변수형 수정 레시피

성공한 `RepairPlan`에서 slide ID, semantic/layout ID와 일회성 precondition을
제거하고 구조 selector와 typed operation으로 request-local recipe를 만든다.
다른 슬라이드에서는 tree path와 구조 shape가 모두 맞을 때만 새 ID로 결합한다.
결합이 모호하거나 불가능하면 재사용하지 않는다.

레시피는 가능한 한 절대 좌표보다 제약과 상대값을 사용한다.

- 필요한 텍스트 높이까지 확장하되 부모의 여유 공간을 넘지 않는다.
- 인접 요소와의 최소 간격을 유지하며 폭 또는 높이를 조정한다.
- 최소 글꼴 크기를 지키면서 줄바꿈과 text-fit을 조정한다.
- 부모 크기나 슬라이드 크기에 대한 비율로 이동량을 계산한다.
- 연결선, 그룹, 표처럼 연동 요소가 있는 경우 constraint footprint 전체를 대상으로 한다.

HTML, 렌더 이미지, acceptance 결과 또는 DB publication receipt는 재사용하지
않는다. 각 슬라이드에서 다시 계산하고 검증한다.

## 6. 충돌 없는 수정의 복합 계획

한 슬라이드에 여러 문제가 있더라도 문제 하나마다 전체 렌더링하지 않는다.
수정 후보 사이에 conflict graph를 만들고 서로 영향을 주지 않는 연산을 하나의
`composite RepairPlan`으로 병합한다.

다음 조건을 모두 만족할 때만 병합한다.

- 대상 노드와 조상·자손 영역이 겹치지 않는다.
- 동일 부모의 공간 배분을 함께 변경하지 않는다.
- constraint footprint가 겹치지 않는다.
- 연결선, 그룹, 표 또는 자동 배치 컨테이너를 공유하지 않는다.
- 병합 후에도 operation, 영향 블록과 geometry budget을 넘지 않는다.

복합 계획이 실패하면 전체 패턴을 포기하지 않는다. 계획을 충돌 단위로 분리해
개별 후보로 다시 시도한다. 서로 영향을 주는 수정은 처음부터 순차 처리한다.

## 7. 후보 탐색과 지연 검증

모든 후보를 미리 렌더링하지 않는다. 성공 가능성과 예상 해결 범위를 기준으로
정렬한 뒤 다음 순서로 필요한 후보만 확장한다.

1. schema, precondition, mutation 범위 검사
2. 정적 DOM·constraint feasibility 검사
3. 변경 영역 중심의 중간 렌더링 검사
4. 슬라이드 전체 Chrome render, OCR, VQA 검사
5. source projection, CAS publish, active read-back, post-verify

저비용 검사나 변경 영역 렌더링만으로 후보를 최종 승인하지 않는다. 대상 이슈가
완전히 해결되고 새 회귀가 없으면 추가 후보 검사를 중단한다. 일부만 해결됐거나
품질 여유가 부족하면 다음 후보를 검사한다.

hard gate를 통과한 후보는 다음 순서로 비교한다.

1. 해결된 상세 이슈 수와 심각도
2. VQA 측정 개선량
3. 개선량 신뢰구간 하한과 상한
4. soft constraint cost
5. 실제 변경 비용
6. stable plan ID

첫 후보가 `acceptance.*`, `constraint.*`, `dom.*`, `invariant.*`, `ocr.*`,
`schema.*`, `vqa.*`와 같은 후보 고유 최종 게이트에서 거절되면 다음 후보를
시도한다. CAS conflict, target missing, transaction failure, read-back failure처럼
외부 상태 또는 게시 무결성이 실패하면 다른 후보를 시도하지 않는다.

## 8. 병렬 실행과 캐시

다음 작업은 bounded worker pool에서 병렬 실행할 수 있다.

- 고속 사전 검사와 fingerprint 생성
- 서로 다른 슬라이드의 후보 생성
- 독립된 렌더링과 OCR/VQA 검사

PowerPoint 갱신, DB publication과 active revision 교체는 슬라이드별 잠금 아래
실행한다. 동일 슬라이드의 여러 수정은 동시에 게시하지 않는다. 브라우저와
렌더링 세션은 제한된 풀로 재사용해 시작 비용과 메모리 경쟁을 함께 줄인다.

폰트, 이미지, 불변 deck asset은 deck 단위로 캐시한다. 검사와 후보 결과는
`slide revision + spec digest + content digest + renderer version`이 모두 일치할
때만 재사용하며 수정이 반영되면 해당 슬라이드 캐시를 무효화한다.

## 9. 탐색 범위와 반복 종료

- 최대 typed operations: 16
- 최대 영향 layout blocks: 8
- 최대 geometry compositions: 8
- 슬라이드별 증분 적용: 최대 12회
- 동일 plan signature 재실행 금지
- 품질 점수나 해결 이슈 수가 개선되지 않는 반복은 중단
- 상반된 연산이 반복되는 진동을 감지하면 해당 후보군 중단
- LLM은 raw HTML/CSS나 페이지를 생성하지 않고 닫힌 `RepairPlan`만 반환
- `setText`, 콘텐츠 삽입·삭제, HTML/CSS/script 직접 변경은 금지

최대 12회는 목표 횟수가 아니라 상한이다. 충돌 없는 수정 병합과 진행성 검사를
통해 일반적인 슬라이드는 훨씬 적은 렌더링으로 종료해야 한다.

## 10. 관측성과 UI

결과에는 다음 지표를 포함한다.

- 문제 슬라이드 수와 상세 이슈 수
- 수정 슬라이드 수와 해결된 상세 이슈 수
- 잔여 슬라이드 수와 잔여 상세 이슈 수
- `pattern_cluster_count`
- `pattern_representative_count`
- `pattern_recipe_count`
- `pattern_reuse_attempts`
- `pattern_reuse_hits`
- `pattern_reuse_applied`
- `composite_plan_count`
- `composite_operations_merged`
- `render_candidates_rejected_early`
- `full_render_count`
- `llm_pattern_call_count`
- `individual_fallback_count`
- 처리 시간과 단계별 소요 시간

UI는 `문제 슬라이드`, `상세 이슈`, `수정 슬라이드`, `해결 이슈`, `잔여 이슈`의
단위를 분리한다. 패턴 분류·레시피·재사용, 병합된 수정과 개별 처리 전환 건수를
표시한다. 잔여 이슈에는 슬라이드 이동과 구체적인 실패 사유를 제공한다.

## 13. 검증과 성능 판정

기능 검증은 다음을 포함한다.

- 패턴 키가 slide-local ID와 무관하게 동일 구조를 묶는지 확인
- 구조 또는 constraint footprint가 다르면 별도 패턴으로 분리하는지 확인
- 표본 편향 없이 매개변수형 레시피가 재결합되는지 확인
- 모호한 target과 절대 좌표 의존 레시피를 거절하는지 확인
- 독립 연산만 복합 계획으로 병합하는지 확인
- 복합 계획 실패 시 개별 후보로 분해되는지 확인
- 패턴 경로 실패 후 개별 규칙 및 LLM 수정계획 경로로 전환되는지 확인
- 후보 고유 게이트 실패 후 차선 후보가 적용되는지 확인
- CAS/read-back 실패에서는 차선 후보를 시도하지 않는지 확인
- 수정 후 캐시가 무효화되고 동일 plan 반복과 진동이 차단되는지 확인
- 자동 페이지 재생성이 호출되지 않는지 확인

현재 방식과 새 방식은 동일한 PPT 집합으로 A/B 비교한다. 새 방식의 승인 조건은
다음과 같다.

- 해결된 상세 이슈 수와 수정 슬라이드 수가 기존 이상
- 새 hard violation, 콘텐츠 손실과 중요 토큰 손실 0건
- 반복 패턴 문서에서 전체 처리 시간과 전체 렌더링 횟수 감소
- LLM 호출 횟수가 기존 이하
- 고유 패턴 문서에서도 군집화 때문에 유의미한 성능 회귀가 발생하지 않음
- 결과가 동일한 입력과 버전에서 재현 가능

목표 성능치는 실제 프로파일링으로 확정한다. 반복 패턴 문서에서는 패턴당 수정법
탐색 횟수와 충돌 없는 수정의 렌더링 횟수를 줄이는 것이 주된 성능 지표다.
