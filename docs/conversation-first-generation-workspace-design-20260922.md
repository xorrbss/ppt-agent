# 생성부터 수정까지 이어지는 대화형 PPT 작업 공간

- 작성일: 2026-09-22
- 개정: v3.1 · 2026-09-23 · 설계 검토의 6개 개선점 반영
- 상태: v3.1 주요 UI 구현 및 기능별 검증 완료. 남은 인수 범위와 요청 수정의 설정 화면 연계는 §15에 기록하며 기존 v2 이력과 구분한다.
- 사용자 결정: 기존 업로드 화면에서 시작하고, 생성 중 전체 화면 채팅으로 진행 내용을 보여준 뒤, 완성되면 왼쪽 PPT와 오른쪽 기존 대화로 전환한다. 오른쪽 채팅도 동일한 대화 중심 디자인으로 통일한다.
- 사용자 추가 결정: 대화 상태 보관, 재시도 종류, 탐색과 수정 대상 분리, 모드별 진행 표시, 가용 폭 기반 반응형, 상태 전이, 주요 화면 명세를 보완한다.
- v3 사용자 결정: 사용자 말풍선·배경 없는 AI 응답, 작은 첨부와 설정 요약, 하나의 대화 스크롤과 고정 입력창, 인라인 진행·오류, 완료 후 왼쪽 PPT와 오른쪽 채팅을 적용한다. 세부 명세는 §13을 따른다.
- v3.1 사용자 결정: 기존 명세 충돌을 해소하고 첨부만 있는 요청의 전송 조건, 수정 대상 해제, 장기 작업 안내, 공통 표현 계층과 구체적인 인수 기준을 보완한다. 개정 대응은 §14를 따른다.
- 이 문서의 구체적인 수치와 신규 컴포넌트 명칭은 구현 명세안이다. 현재 동작이나 검증 완료 사실을 의미하지 않는다.
- 관계: `chat-first-slides-workbench-design-20260802.md`의 영속 대화·작업·이벤트 계약을 유지하면서, 최초 생성 진입과 화면 배치를 구체화한다. 이전 문서의 모든 기능을 이번 구현 범위로 확대하지 않는다.

## 1. 사용자 경험과 범위

사용자는 요청을 한 번 보내고, 같은 대화에서 제작 과정을 확인하며, 완성된 PPT를 옆에 펼쳐 수정한다. 화면 크기가 바뀌어도 최초 요청, 첨부 자료, 작업 결과, 입력 중인 문장은 유지된다.

포함 범위:

- 업로드의 생성 시작 이후 로딩 팝업과 중간 화면 이동을 대화형 진행 화면으로 통합한다.
- 구성 검토 옵션을 선택한 경우 같은 대화 안에서 확인·수정·생성 시작을 처리한다.
- 생성 완료 시 왼쪽 결과 영역을 열고, 오른쪽에 기존 대화를 유지한다.
- 편집 화면의 메시지, 진행 표시, 입력창, 수정 대상 표시를 통일한다.
- 대기, 연결 끊김, 실패, 재시도, 취소, 재접속을 같은 공간에서 처리한다.

유지 범위:

- 기존 업로드 파일 선택, 요청 작성, 디자인·장수·언어 설정.
- 생성 모드별 파이프라인, 품질 기준, 원문 보존 정책, 내보내기 방식.
- 기존 슬라이드 렌더러와 직접 편집 기능, 권한과 서버의 작업 승인 규칙.
- OS 파일 선택기와 일시적인 편집 팝오버. 진행 팝업을 없앤다는 이유로 모든 팝업을 제거하지 않는다.

1차 구현에서 생성 중 자유로운 추가 지시의 즉시 반영이나 자동 예약 전송은 제공하지 않는다. 초안은 작성할 수 있고, 생성이 끝난 뒤 사용자가 직접 전송한다.

## 2. 화면 구성

| 상태 | 본문 | 하단 입력창 | 주 행동 |
|---|---|---|---|
| 생성 전 | 기존 업로드 화면과 디자인 선택 | 기존 요청 입력 | 만들기 |
| 접수·자료 처리 | 중앙 대화, 최초 요청·첨부, 현재 처리 상태 | 초안 작성 가능, 수정 요청 전송 불가 | 지원되는 경우 취소 |
| 구성 검토 필요 | 같은 대화 안의 실제 목차와 검토 영역 | 초안 보존, 일반 수정 요청 전송 불가 | 구성 수정·이대로 만들기 |
| 생성 중 | 중앙 대화, 실제 구성, 갱신되는 진행 영역 | 초안 작성 가능, 전송 불가 | 지원되는 경우 취소 |
| 생성 완료·결과 로딩 | 완료 상태와 결과 준비 안내 | 초안 보존 | 결과 조회 재시도 |
| 결과 준비 완료 | 왼쪽 PPT, 오른쪽 기존 대화 | 수정 요청 전송 가능 | 수정·발표·내보내기 |
| 실패·취소 | 마지막 상태와 설명을 대화 안에 유지 | 초안 보존 | 허용되는 재시도·조건 수정 |

### 2.1 전체 화면 대화

- 앱 상단에는 뒤로 가기, 자료 제목 또는 임시 제목, 필요한 최소 메뉴만 표시한다.
- 생성 시작 후 디자인 갤러리와 큰 안내 제목은 접는다. 기존 전역 탐색 메뉴는 작업 집중을 위해 접힌 상태로 표시한다.
- 대화 본문 최대 폭은 800px, 좌우 여백은 화면에 따라 16~32px로 정한다. 입력창과 본문의 정렬선을 일치시킨다.
- 처음부터 하단에 입력창을 고정한다. 메시지 영역만 스크롤되며 마지막 메시지가 입력창에 가려지지 않는다.
- 첫 사용자 메시지는 클릭 시점의 요청·첨부·설정 스냅샷이다. 파일만 보낸 경우 파일과 중립적인 생성 요청 안내를 표시하고 사용자가 쓰지 않은 문장을 원문 프롬프트로 표시하지 않는다.
- 설정은 ‘15장 · 한국어 · 선택한 디자인’처럼 짧게 표시하고 상세는 펼쳐 본다.

### 2.2 완료 후 작업 공간

- 왼쪽은 썸네일 목록과 큰 슬라이드, 오른쪽은 기존 대화다. 대화 본문과 입력 초안을 새로 생성하지 않는다.
- 최초 분할은 왼쪽 PPT 약 65%, 오른쪽 채팅 약 35%를 기본으로 한다. 채팅 최소 360px·최대 600px와 PPT 최소 폭을 우선하며, 사용자가 조정한 폭은 보존한다. 경계선 드래그만으로 탭 배치로 전환하지 않는다.
- 경계선은 마우스·키보드로 조절할 수 있다. 채팅을 접고 다시 펼치는 버튼을 제공한다.
- 썸네일 영역은 기본 약 112px이며 접을 수 있다. 기존 문서 비율을 그대로 사용하므로 세로형·A4도 강제로 16:9에 맞추지 않는다.
- 발표·다운로드·직접 편집은 PPT 영역의 상단에 배치한다. 채팅 상단에 동일한 버튼들을 중복 나열하지 않는다.
- 전환 애니메이션은 약 200ms이며 움직임 줄이기 설정에서는 생략한다. 자동 전환이 키보드 초점을 빼앗지 않는다.
- 완료 직후 기존 대화의 생성 과정은 ‘제작 과정 보기’로 접는다. 최초 요청과 완료 결과는 보인다. 사용자가 해당 내역을 읽거나 조작 중이면 즉시 접지 않고 읽기 위치를 보존한다.

### 2.3 반응형

- 기준은 브라우저 전체 폭이 아니라 전역 메뉴·바깥 여백을 제외한 작업 컨테이너의 가용 폭 W다. 창 크기와 사이드바 변경에 따라 다시 계산한다.
- PPT 패널 최소 폭 600px(내부 여백 포함), 채팅 최소 폭 360px, 구분선 영역 8px로 정한다. W가 968px 이상이면 분할, 그 미만이면 ‘PPT / 채팅’ 탭이다. 생성 중에는 폭에 관계없이 전체 대화다.
- 분할 시 최초 선호 폭은 `0.35 × W`다. 실제 채팅 폭은 `min(max(선호 폭, 360), 600, W - 608)`로 제한한다. 사용자가 조절하면 저장된 선호 폭을 사용한다. 예를 들어 W=1000px이면 최초 채팅 폭은 360px, 조절 가능한 최대 폭은 392px다.
- 드래그는 해당 범위에서만 동작하며 범위를 넘겨 탭 전환을 유발하지 않는다. 실제 컨테이너가 작아지는 경우에만 탭으로 전환한다.
- W가 1080px 미만이면 썸네일 목록을 자동으로 접어 PPT 본문 공간을 확보한다. 사용자는 목록을 임시 패널로 열 수 있다.
- 창이 좁아져 적용 폭이 줄어도 저장된 선호 폭을 덮어쓰지 않는다. 다시 넓어지면 선호 폭과 이전 탭·접힘 선택을 복원한다.
- 좁은 화면에서 완성되면 PPT 탭을 기본으로 연다. 입력창에 초점이 있거나 이전 대화를 읽는 중이면 채팅을 유지하고 ‘PPT 보기’ 버튼으로 알린다.
- 작은 화면의 슬라이드 목록은 접이식 패널로 제공한다. 화면 키보드가 열려도 입력창과 전송 버튼에 접근할 수 있어야 한다.

## 2.4 주요 화면 와이어프레임

아래는 구현용 구조 명세다. 예시 문구·장수는 실제 작업 데이터로 대체하며, 코드나 완성된 화면 캡처가 아니다. 공통 상단 아래의 메시지 영역만 스크롤하고 입력창은 고정한다.

**A. 생성 중 — 현재 단계와 요청 맥락을 함께 유지**

```text
┌──────────────── 제목 · 생성 중 ────────────────┐
│             중앙 대화 / 최대 800px              │
│       [사용자 요청, 파일 2개, 설정 요약]          │
│                                                 │
│  접수한 자료를 바탕으로 제작하고 있습니다.       │
│  ▸ 구성 보기  (실제 구성 데이터가 있을 때만)     │
│  ● 슬라이드 제작 · 15장 중 8장 완료             │
│  ▸ 제작 과정                    [생성 중단]      │
│                                                 │
├─────────────────────────────────────────────────┤
│  [완성 후 보낼 수정 요청을 작성하세요 …]         │
│  생성이 끝나면 전송할 수 있어요.        [↑ 잠김] │
└─────────────────────────────────────────────────┘
```

주 행동은 허용된 경우 ‘생성 중단’. 첨부 3개 이상은 첫 2개와 ‘파일 더 보기’로 접고, 긴 최초 요청은 6줄 미리보기와 펼치기를 제공한다. 진행 상태는 접힌 요청 바로 아래에서 계속 확인할 수 있다.

**B. 선택 대기 — 질문과 행동을 같은 영역에 배치**

```text
┌──────────────── 제목 · 구성 확인 ──────────────┐
│  [최초 요청 요약]                                │
│  아래 구성으로 만들까요?                         │
│  ┌ 실제 목차 / 대화 목록과 함께 스크롤 ┐        │
│  │ 1. 배경   2. 현황   3. 제안 …     │        │
│  └───────────────────────────────────┘        │
│              [구성 수정] [이대로 만들기]         │
├─────────────────────────────────────────────────┤
│  [보존된 수정 초안 …]                   [↑ 잠김] │
└─────────────────────────────────────────────────┘
```

주 행동은 ‘이대로 만들기’. ‘구성 수정’은 같은 영역을 편집 가능하게 하고 ‘수정 적용 / 변경 취소’를 제공한다. 하단의 완성 후 수정 초안과 구성 편집값은 별도로 보관한다. 원문 처리 선택도 이 배치를 사용하되 기존 선택 설명과 필수 동의를 보존한다.

**C. 완성 후 — 보기와 수정 대상을 분리**

```text
┌──────────── 제목 ───── [발표] [다운로드] ───────┐
│ 목록 │                                  │ 대화 │
│  1   │           큰 PPT 화면            │ 요청 │
│  2   │                                  │ ▸과정│
│  3   │         [이 슬라이드 수정]        │ 완료 │
│      │                                  │      │
│      │                                  ├──────┤
│      │                                  │범위 ▾│
│      │                                  │초안 ↑│
└─────────────────────────────────────────────────┘
```

주 행동은 채팅의 ‘수정 요청 전송’. PPT의 발표·내보내기도 그대로 제공한다. ‘이 슬라이드 수정’을 누르면 해당 ID가 입력창의 대상이 되고 초점이 입력창으로 이동한다. 단순 썸네일 클릭은 보기만 바꾼다.

**D. 실패·재시도 — 오류 종류에 맞는 행동만 제공**

```text
┌──────────────── 제목 · 작업 중단 ──────────────┐
│  [최초 요청과 첨부 요약]                         │
│  이번 시도에서 자료 처리를 완료하지 못했습니다.  │
│  ▸ 확인 가능한 설명과 마지막 단계               │
│  [같은 요청 재시도]  [요청 수정]                 │
│  ┌ 요청 수정 선택 시 인라인 편집 영역 ┐        │
│  │ 파일 / 프롬프트 / 설정             │        │
│  │ [변경 취소] [변경한 요청으로 만들기] │        │
│  └───────────────────────────────────┘        │
├─────────────────────────────────────────────────┤
│  [완성 후 수정 초안은 별도 보존]         [↑ 잠김]│
└─────────────────────────────────────────────────┘
```

재시도 가능 여부는 서버 기준이다. 응답 유실이면 ‘접수 상태 확인’, 결과 조회 실패이면 ‘PPT 다시 불러오기’를 주 행동으로 바꾸며 생성 재시도 버튼으로 대체하지 않는다.

**E. 모바일 완료 화면 — 한 번에 하나의 작업 영역**

```text
┌──── 제목 ─────── [메뉴] ┐
│ [PPT]   [채팅 · 새 소식]│
│ [목록]                 │
│                        │
│       큰 PPT 화면      │
│                        │
│ [이 슬라이드 수정]     │
└────────────────────────┘
```

PPT 탭의 ‘이 슬라이드 수정’은 대상을 고정하고 채팅 탭으로 이동한다. 채팅 탭에서는 A와 같은 고정 입력창을 사용한다. 입력 중 생성이 완료되면 채팅을 유지하고 ‘PPT 보기’를 표시한다. 실패·필수 선택은 해당 탭에 배지로 알리되 입력 초점을 강제로 이동하지 않는다.

## 3. 대화와 진행 표시

### 3.1 메시지 디자인

- 사용자: 오른쪽 정렬, 연한 중성 회색 배경, 최대 폭 85%, 과도한 테두리·그림자 없음.
- AI: 왼쪽 정렬, 배경 박스 없이 본문 중심, 기본 14~15px와 약 1.6의 행간. 패널 안쪽 여백 20px, 메시지 사이 24px를 제안한다.
- AI 본문은 안전한 Markdown 렌더링을 지원하되 HTML 실행은 허용하지 않는다. 넓은 표는 해당 표 안에서만 수평 스크롤하고, 긴 본문·목차·작업 내역은 대화 목록의 세로 스크롤을 공유한다. 별도의 세로 스크롤 카드를 만들지 않는다.
- 첨부는 파일명·파일 종류·상태를 작은 항목으로 표시한다. 다운로드·미리보기는 실제 자산 권한과 상태를 따른다.
- 정상 연결 상태는 상시 배지로 강조하지 않는다. 연결 문제가 생겼을 때만 읽기 쉬운 안내를 표시한다.
- 응답 전체를 임의로 타이핑 효과로 재생하지 않는다. 실제 응답 스트림이 있는 경우에만 스트리밍한다.

### 3.2 하나의 작업, 하나의 진행 영역

- 한 생성 작업에는 한 진행 영역만 존재한다. 이벤트마다 말풍선이나 카드를 추가하지 않는다.
- 기본 표시: 현재 단계 한 줄, 확인 가능한 완료 장수, 펼칠 수 있는 작업 내역, 허용되는 행동.
- 구성이나 자료 요약이 실제로 준비되면 같은 생성 응답 안에 표시한다. 별도 LLM 호출로 진행 설명을 꾸며내지 않는다.
- 요약 데이터가 없다면 ‘자료를 읽고 있습니다’ 같은 사실적 안내만 표시한다. 모드에 목차 단계가 없다면 목차를 만들어서 보여주지 않는다.
- 장수 집계는 의미가 확인된 단계에만 표시한다. 15/15 제작 후 저장·검수가 남아 있다면 ‘15장 제작 완료 · 마무리 중’으로 표시한다.
- 재시도에서 카운트가 초기화되면 새로운 시도임을 표시한다. 숫자를 억지로 단조 증가시키지 않는다.
- 총량이 없으면 단계만 보여준다. 시간 기반 가상 퍼센트나 검증되지 않은 남은 시간은 표시하지 않는다.
- 대기열, 사용자 선택 대기, 실제 생성 중을 구분한다. 대기열 위치도 서버가 제공할 때만 표시한다.

### 3.2.1 모드별 표시 계약과 최소 화면

아래는 UI 표시 계약이며 각 데이터의 현재 제공 여부를 보증하는 표가 아니다. 구현 시 모드별 기존 응답에 연결하고, 데이터가 없는 칸은 명시된 최소 화면을 적용한다.

| 경로 | 표시할 수 있는 실제 데이터 | 데이터 부재 시 필수 표시 | 완료 전 확인할 사항 |
|---|---|---|---|
| 공통 파일 처리 | 첨부 목록, 처리 완료 파일 수, 처리 상태 | 접수된 요청·파일·설정 요약과 마지막 확인 상태 | 영속 자산과 요청 연결 여부 |
| Authored / SVG | 저장된 구성, 현재 제작 단계, 의미가 확인된 완료 장수 | 요청 요약 + 실제 단계 + 작업 내역 | 단계별 장수의 의미, 결과 ID·리비전 |
| 원문 기반 생성 | 확정된 원문 처리 선택, 공개 가능한 자료 구성, 실제 제작 진행 | 원문 처리 선택 요약 + 작업 상태 | 기존 내용 보존·필수 선택 계약 유지 |
| Template-v2 | 준비된 개요, 레이아웃 선택·제작·저장 등 실제 단계 | 요청 요약 + 현재 확인된 단계 | 검수·저장·게시와 화면용 결과 준비의 관계 |
| 기타 기존 템플릿/호환 경로 | 해당 경로가 실제 제공하는 개요·진행 | 같은 최소 화면 | 공통 작업 상태 연결 전에는 신규 UX 적용 완료로 간주하지 않음 |

- 어느 모드에서도 비어 있는 전체 화면에 스피너만 표시하지 않는다. 요청·파일·설정 요약과 마지막 확인 상태가 최소 화면이다.
- 목차를 단계적으로 보여줄 수 있는 모드라도 미확정 구성을 ‘확정’으로 표시하지 않는다. 검토가 필요한 구성은 검토 상태를 명시한다.
- 최신 서버 상태 확인 시각과 마지막 실제 진행 변화 시각을 구분한다. 60초 이상 진행 변화가 없을 때의 안내는 §13.4.1을 따른다. 조회 성공이나 heartbeat로 진행 변화 시각을 갱신하지 않으며, 이는 실패 판정이나 자동 재시도 기준이 아니다.
- 연결 자체를 확인할 수 없으면 처리 중이라고 단정하지 않고 ‘연결을 확인하고 있습니다’로 표시한다. 수동 상태 확인은 기존 조회 경로를 재사용하며 별도 폴링 루프를 만들지 않는다.
- ‘15/15’ 뒤 검수·저장이 남아 있는 모드는 마무리 상태로 이어진다. 중간 데이터 지원 수준은 구현 결과에 모드별로 기록한다.

### 3.3 선택과 승인

- ‘구성 먼저 검토’ 옵션이 켜졌다면 생성 전에 인라인 목차 검토를 제공한다. 기본 자동 생성 경로에는 새 확인 단계를 추가하지 않는다.
- 원문 처리 선택 등 기존 필수 질문은 원래의 설명·선택 결과를 유지하면서 인라인으로 이동한다.
- 승인·거절·취소·재시도는 서버에서 허용한 행동만 표시한다. UI가 임의로 허용 상태를 만들지 않는다.
- 요청 처리 중에는 해당 행동의 중복 제출을 막는다. 승인 응답이 유실되면 상태를 먼저 조회한다.

## 4. 입력창과 수정 경험

- 둥근 하나의 입력 영역 안에 첨부 버튼과 전송 아이콘을 둔다. 입력 높이는 내용에 따라 증가하고 최대 높이 이후 내부 스크롤을 사용한다.
- Enter는 전송, Shift+Enter는 줄바꿈이며 한글 IME 조합 확정 중 Enter는 전송하지 않는다.
- 생성 중에도 초안 편집은 가능하다. ‘생성이 끝나면 수정 요청을 보낼 수 있어요’라고 안내하고 전송 및 새 첨부 제출은 비활성화한다. 완료 시 자동 전송하지 않는다.
- 생성 취소가 지원되면 입력창 전송 위치에 ‘생성 중지’를 표시하고 해당 실행 operation에 연결한다. 취소 요청 중에는 중복 실행을 막는다. 이는 서버 작업 취소 요청이며 화면 응답 스트림만 닫는 기능이 아니다. 별도 중복 취소 버튼은 추가하지 않는다.
- PPT 최초 표시 시 수정 범위는 ‘대상 선택’이다. 사용자가 ‘전체 발표자료’ 또는 특정 슬라이드를 명시적으로 선택하기 전에는 수정 요청을 전송하지 않는다. 최초 생성 요청에는 수정 대상 선택을 요구하지 않는다.
- 썸네일 클릭·스크롤·발표 이동은 보기만 바꾼다. 입력창에는 ‘대상 선택 / 전체 발표자료 / 선택한 슬라이드’ 상태를 표시한다.
- ‘현재 슬라이드’를 선택하거나 PPT의 ‘이 슬라이드 수정’을 누르는 순간 해당 슬라이드 ID를 고정하고 ‘3번 슬라이드 ×’로 표시한다. 이후 다른 장을 보더라도 고정 대상은 바뀌지 않는다. ×는 ‘대상 선택’으로 되돌리고 전송을 막으며, 전체 자료로 자동 확대하지 않는다. 초안·첨부는 유지한다.
- 전송할 때 대상의 안정적인 슬라이드 ID와 기준 리비전을 고정한다. 실행 중 다른 슬라이드를 선택해도 진행 중인 요청의 대상은 바뀌지 않는다.
- AI가 결과 슬라이드를 자동으로 보여주는 동작은 다음 요청의 대상을 몰래 바꾸지 않는다. 입력 중 대상을 바꾸면 변경된 범위를 눈에 띄게 표시한다.
- 전송된 사용자 메시지에도 당시 수정 범위를 표시한다. 슬라이드 삭제로 대상이 무효가 되면 전송을 막고 범위를 다시 고르게 한다. 순서 변경 시 같은 ID를 유지하고 표시 번호만 갱신한다.
- 자유문이 명시된 범위와 충돌하면 실행 전에 인라인으로 범위를 확인한다. 예를 들어 ‘전체 자료’ 선택 상태의 ‘3번만 고쳐줘’를 조용히 전체 수정으로 처리하지 않는다. 현재 서버의 범위 해석 계약으로 해결되지 않는 경우 필요한 확인 응답을 기존 명령 계약에 추가한다.
- 수정 결과는 변경 내용을 짧게 설명하고 ‘슬라이드 보기’, 지원되는 경우 ‘되돌리기’를 붙인다. 서버가 확인하지 않은 변경 내용을 표시하지 않는다.
- 추천 요청은 첫 완료 직후 또는 빈 대화에서 최대 3개만 표시한다. 클릭하면 입력 초안에 채우며 바로 전송하지 않는다.

## 5. 상태와 완료 조건

화면 배치, 서버 작업, 연결, 내보내기 상태를 분리한다. 연결 끊김을 작업 실패로 바꾸거나 PPTX 준비를 슬라이드 완료와 동일시하지 않는다.

| 축 | 설계상 상태 |
|---|---|
| 화면 | 업로드 / 전체 대화 / PPT와 대화 |
| 작업 | 접수 / 자료 처리 / 구성 / 선택 대기 / 생성 / 마무리 / 성공 / 실패 / 취소 요청 중 / 취소 |
| 연결 | 연결 중 / 실시간 / 조회 방식 대체 / 오프라인 |
| 결과 | 없음 / 조회 중 / 사용 가능 / 조회 실패 |
| 내보내기 | 미시작 / 준비 중 / 사용 가능 / 실패 |

왼쪽 PPT 자동 열림은 다음 조건이 모두 충족될 때 한 번만 실행한다.

1. 해당 생성 작업의 서버 상태가 성공이다.
2. 서버가 지정한 결과 presentation ID와 리비전으로 결과를 조회했다.
3. 해당 모드의 결과 자료를 기존 뷰어에 전달할 수 있다.

슬라이드가 일부 존재하거나 카운트가 총 장수에 도달했다는 이유로 성공 처리하지 않는다. 서버 성공 후 결과 조회가 실패하면 ‘PPT를 불러오지 못했습니다’와 조회 재시도를 제공한다. 이때 생성 작업을 다시 실행하지 않는다. 파일 내보내기 실패도 이미 완성된 PPT를 숨기지 않는다.

자동 전환 이후 사용자가 채팅을 접거나 탭을 바꿨다면 후속 중복 완료 이벤트가 이를 되돌리지 않는다.

### 5.1 상태 전이와 행동

모든 작업 이벤트는 workspace·attempt·operation 식별자에 먼저 귀속시킨다. 다른 시도의 이벤트를 현재 시도에 적용하지 않는다. 다음 표의 버튼도 서버 권한·허용 행동이 확인된 경우에만 활성화한다.

| 현재 상태 | 수신 이벤트 / 사용자 행동 | 다음 상태 | 허용 행동과 화면 변화 |
|---|---|---|---|
| 접수 중 | 서버 응답 유실 | 접수 여부 확인 중 | 기존 키로 상태 확인, 새 생성·조건 변경 제출 금지 |
| 자료 처리·생성 중 | 사용자 선택 요청 | 선택 대기 | 인라인 선택·승인, 일반 수정 전송은 계속 금지 |
| 선택 대기 | 승인 접수 | 실행 중 | 중복 승인 차단, 작업 진행 영역 갱신 |
| 실행 중 | 취소 접수 | 취소 요청 중 | 추가 취소·재시도 차단, 서버 최종 결과 대기 |
| 취소 요청 중 | 서버 성공 확정 | 성공 / 결과 조회 중 | 취소 성공으로 표시하지 않음, 결과 조회 |
| 취소 요청 중 | 서버 취소 확정 | 취소 | 지원되는 재시도 또는 요청 수정 |
| 실행 중 | 서버 실패 확정 | 실패 | 동일 요청 재시도·요청 수정 중 허용된 행동 |
| 성공 / 결과 조회 중 | 결과 조회 실패 | 성공 / 결과 조회 실패 | 결과 조회만 재시도, 새 생성 금지 |
| 성공 / 결과 조회 중 | 결과 준비 | 성공 / 결과 사용 가능 | 해당 결과에 대해 최초 한 번 PPT 열기 |
| 결과 사용 가능 | 중복 완료 이벤트 | 유지 | 결과·완료 메시지 중복 생성 금지, 사용자 배치 유지 |
| 새 시도 실행 중 | 이전 시도의 늦은 이벤트 | 현재 시도 유지 | 이전 시도의 기록만 갱신, 현재 PPT 자동 교체 금지 |
| 어떤 작업 상태든 | 연결 끊김·복구 | 작업 상태 유지 | 연결 축만 변경, 복구 후 cursor 기준 재연결 |
| 결과 사용 가능 | 수정 작업 접수 | 결과 유지 / 수정 중 | 기존 PPT 유지, 다른 변경 요청은 초안 작성만 허용 |
| 수정 중 | 수정 성공 | 최신 결과 조회·반영 | 초안은 유지, 자동 전송 금지, 해당 수정의 결과 표시 |
| 수정 중 | 수정 실패·리비전 충돌 | 기존 결과 유지 | 상태 갱신 후 허용된 재시도·대상 확인 |

- 성공·실패·취소 등 최종 상태가 서로 충돌하면 이벤트 도착 순서로 덮어쓰지 않는다. 서버 최신 스냅샷과 operation version으로 확인한다.
- 1차 UI는 같은 자료에 대한 사용자 변경 요청을 하나씩 제출한다. 수정 진행 중에도 초안은 편집할 수 있지만 전송은 막고 자동 대기열에 넣지 않는다. 조회·내보내기·직접 편집의 가능 여부는 기존 서버 충돌 정책을 따른다.
- 자동 열기 처리 키는 결과 presentation ID·리비전·완료 operation ID로 구성하고 브라우저 세션에 보관한다. 최초 진입은 서버 결과에 맞춰 초기 배치하되 반복 이벤트가 접힘·탭 선택을 취소하지 않는다.

제안하는 컴포넌트 책임:

- 공통 작업 공간: 레이아웃, 작업 연결, 결과 준비 여부, 초안·스크롤·선택 대상 보존.
- 공통 채팅 표면: 메시지·진행·입력창. 전체 화면과 패널은 배치 속성만 다르다.
- 생성 진행 표시: 기존 operation을 사용자용 단계와 실제 내용으로 투영한다.
- PPT 패널: 기존 뷰어·썸네일·편집 기능을 감싼다.
- 기존 작업 hook: 네트워크와 요청 재시도 책임. 표시 컴포넌트가 생성 API를 직접 재호출하지 않는다.

위 책임을 분리하되 새 서버 대화 저장소나 새 생성 엔진을 도입하지 않는다. 표시 컴포넌트의 생존만으로 상태 보존을 보장하지 않으며, 다음 소유권을 기준으로 기존 UI 상태를 상위로 이동한다.

### 6.1 공통 화면과 상태 소유권

- `(presentation-generator)/layout.tsx`의 기존 인증·설정 경계 안에 있는 `GenerationWorkspaceProvider`를 상태 보관 경계로 재사용한다. §12에 기록된 provider와 준비/편집 화면 간 전달 방식을 현행 기준으로 삼는다.
- 준비 화면과 기존 편집 화면의 생존 범위를 유지하고, provider로 초안·첨부·대상·읽기 위치·초점 복원 정보를 전달한다. 별도의 거대한 host를 신설하거나 기존 `PresentationPage`를 중복 마운트하지 않는다. 공통화 범위는 §13.8.1의 표시 컴포넌트와 표현 데이터 계약이다.
- `/upload`에서 제출하면 준비 화면이 전체 대화를 표시한다. 영속 presentation ID 확보 후 기존 경로 전환으로 재접속 주소를 만들며 동일 작업의 상태와 초점을 전달한다. 생성 시작은 기존 실행 controller가 담당하며 provider 또는 컴포넌트 마운트가 새 실행 루프를 만들지 않는다.
- `/outline` 직접 링크는 기존 구성 검토 진입점으로 유지하고 공통 provider를 사용한다. 기존 auto 인자는 기존 요청이 없는 경우에만 기존 중복 방지 절차로 처리한다. 주소 이동 자체를 두 번째 생성 요청으로 해석하지 않는다.
- 기존 `/presentation` 직접 진입은 ID의 상태를 조회해 생성 중 전체 대화 또는 완성된 분할 화면을 선택한다. 기존 발표 모드 등 명시적인 URL 동작은 기존 경로를 유지한다.
- 이탈하면 화면 구독은 해제할 수 있지만 서버 작업 취소로 간주하지 않는다. 명시적 취소만 서버에 전달한다. 이전 작업의 비동기 응답이 새 경로의 작업을 활성화하지 못하게 식별자를 검사한다.

| 데이터 | 원본 / 소유자 | 복원 범위 |
|---|---|---|
| 대화·작업·결과·리비전·허용 행동 | 기존 서버 workspace | 로그인 권한 확인 후 재조회 |
| 업로드 전 File 객체 | provider의 작업별 메모리 | 같은 탭의 경로·패널 전환만 보장, 새로고침 후 재첨부 가능 |
| 전송 전 초안·범위·준비된 첨부 ID | provider + 사용자·작업별 sessionStorage | 같은 탭 재접속·새로고침, 첨부 상태 재검증 후 복원 |
| 서버 등록 전 요청 원문·설정 | provider 메모리의 고정 스냅샷 | 영속 첫 메시지가 저장되면 서버를 기준으로 전환 |
| 시도별 요청 키·자산 snapshot ID·서버 ID 연결 | 기존 durable-task 저장과 작업별 복구 메타데이터 | 기존 보존 계약을 유지하며 사용자 소유권 확인 후 조회 |
| 스크롤 앵커·탭·채팅 선호 폭·초점 복원 힌트 | provider + 작업별 sessionStorage | 같은 탭에서 작업을 오갈 때 복원 |

- 새로운 초안 저장은 localStorage로 확대하지 않는다. 인증 토큰·File 바이너리를 저장하지 않으며 로그아웃·계정 변경 시 사용자별 메모리와 sessionStorage를 정리한다. 저장 불가 환경에서는 현재 화면 메모리만 유지하고 새로고침 복원 한계를 알린다.
- 초안 저장은 자동 전송 권한을 뜻하지 않는다. 다른 PPT로 이동하면 workspace 키별 초안을 사용하며 이전 자료의 파일·대상을 섞지 않는다.
- 스크롤은 픽셀 값만 저장하지 않고 메시지 ID와 그 메시지 내 상대 위치를 기준으로 복원한다. 전체 화면에서 패널로 줄어 재줄바꿈되어도 읽던 메시지를 유지한다.
- 작업 간 이동 후에는 임의로 입력창을 자동 포커스하지 않는다. 같은 작업의 배치 전환에서만 기존 초점을 복원한다.

## 7. 생성 시작과 데이터 연결

### 7.1 접수부터 영속 작업까지

1. 사용자가 만들기를 누르면 먼저 기존 필수 입력 검증을 수행한다. 입력 오류는 업로드 화면에 표시한다.
2. 유효한 요청을 클릭 시점 스냅샷으로 고정하고 즉시 전체 대화 UI를 표시한다. 서버 저장 전 첫 메시지는 ‘접수 중’으로 표시한다.
3. 기존 업로드 admission과 문서 처리 흐름을 실행한다. UI 전환·두 번 클릭·재접속이 별도 생성 요청을 만들지 않게 한다.
4. 기존 생성 준비 경로에서 발급한 presentation/task/operation 식별자에 대화를 연결한다. 서버 메시지가 도착하면 임시 메시지를 대체하고 중복으로 추가하지 않는다.
5. 영속 식별자를 얻은 뒤 주소를 작업 재접속이 가능한 주소로 갱신한다. 사용자는 동일한 작업 공간을 계속 보며, 주소 변경만으로 컴포넌트가 초기화되지 않게 한다.
6. 완료 후 같은 작업과 연결된 결과를 조회하여 왼쪽 패널을 연다.

기존 `/outline` 직접 진입과 `/presentation` 링크는 §6.1의 호환 진입점으로 유지한다. 일반 생성 흐름에서는 중간 개요 페이지를 렌더링하지 않는다. 단순히 `router.push` 목적지만 바꾸는 방식으로 생성 시작을 누락시켜서는 안 된다.

### 7.1.1 요청·시도·메시지 연결

- workspace는 사용자가 보는 대화 단위, attempt는 입력 스냅샷이 고정된 한 번의 생성 시도다. 서버 ID가 없는 동안만 로컬 workspace 키를 사용하고, 서버 ID 발급 후 기존 상태를 별칭으로 연결한다.
- 각 attempt는 클라이언트 요청 식별자, 변하지 않는 입력 snapshot, API 단계별 idempotency key와 확인된 task/operation/presentation ID를 가진다. 서로 다른 API의 키를 하나로 합치지 않는다.
- 임시 첫 메시지 ID는 attempt의 요청 식별자에서 정한다. 서버의 저장된 첫 메시지 ID를 응답 또는 조회 결과로 연결한 뒤 같은 표시 위치에서 교체한다. 프롬프트 문자열 일치만으로 새 경로의 중복 여부를 결정하지 않는다.
- API가 요청 식별자와 서버 첫 메시지의 연결을 제공하지 않는 경우 기존 접수 응답 또는 workspace projection에 최소 연결 필드를 추가한다. 해당 연결은 신규 UX 활성화 전 충족해야 할 계약이다.
- 서버 ID를 얻는 것만으로 이전 요청의 입력이나 키를 변경하지 않는다. 계정 권한이 확인되지 않는 로컬 복구 항목은 표시·재실행하지 않는다.

### 7.2 진행 데이터의 우선순위

- 서버 workspace 타임라인과 operation이 작업 상태의 기준이다. 기존 모드별 상태 API는 연결 정보가 아직 없는 구간 또는 명시된 호환 경로에서만 사용한다.
- 자료 처리 완료 파일 수는 document progress에서, 생성 완료 장수·현재 단계는 generation progress에서 가져온다.
- author·illustrate·render·persist·finalize 및 template-v2 단계는 사용자용 표현으로 변환한다. 모든 모드가 동일한 순서로 진행한다고 가정하지 않는다.
- 구성·요약은 저장된 실제 산출물에 기반한다. 공개 가능한 데이터가 없는 모드는 단계 표시만 지원한다.
- 동일 이벤트의 중복 수신과 역순 수신은 기존 cursor·sequence·operation version 규칙으로 처리한다. 화면 시각만으로 순서를 결정하지 않는다.
- 서버 첫 메시지가 원본 요청의 기준이며 generation metadata 보완 메시지보다 우선한다.

구현 전에 확인할 좁은 미확인 사항:

- 각 생성 모드에서 영속 presentation/operation 식별자가 생기는 시점과 문서 처리 이전 복구 가능 범위.
- 중간 목차·자료 요약이 권한 확인된 API로 제공되는지, 어느 모드에서 제공되는지.
- 원문 처리·구성 검토 선택을 현재 제출 경로에 인라인으로 연결하는 데 필요한 최소 인터페이스.
- §6.1의 기존 provider와 준비/편집 화면을 연결할 구체적인 코드 분리 범위와 §7.1.1의 서버 메시지 상관관계 필드 제공 여부.

기존 응답으로 부족한 경우에만 기존 작업 계약에 필요한 필드를 추가한다. 조사하지 않은 백엔드 기능을 이미 지원한다고 가정하지 않는다.

## 8. 실패·복구·접근성

- 새로고침: 영속 작업이 있으면 저장된 요청·타임라인·결과를 조회하고 진행을 재연결한다. 마운트 자체가 새 생성 POST를 유발하지 않는다.
- 영속화 전 새로고침: 브라우저 File 객체 복원은 보장하지 않는다. 완료된 업로드 자산과 진행 작업을 먼저 확인하고 필요할 때만 재첨부를 요청한다.
- 네트워크 단절: 마지막 상태를 유지하고 ‘연결을 다시 확인하고 있어요’라고 표시한다. 서버 작업을 실패·취소로 단정하지 않는다.
- 접수 응답 유실: 기존 idempotency key로 결과를 확인하거나 기존 정책대로 재시도한다. 새 키로 중복 작업을 시작하지 않는다.
- 실패: 이해 가능한 원인과 허용되는 행동을 표시한다. 내부 예외·경로·원문 로그를 대화에 노출하지 않는다.
- 취소: 서버 확인 전에는 ‘중단 요청 중’이다. 취소와 완료가 경합하면 서버 최종 상태를 따른다.
- 재시도: 기존 작업의 허용 행동과 체크포인트 정책을 따른다. 서버 근거 없이 ‘이어서 생성’이라고 약속하지 않는다.
- 범위 충돌: 사용자가 보는 리비전과 서버 리비전이 다르면 기존 충돌 정책으로 갱신 후 재확인한다.
- 자동 스크롤: 하단을 보고 있을 때만 따라간다. 이전 메시지를 읽는 중이면 ‘새 메시지’ 이동 버튼을 제공한다.
- 키보드: 패널 구분선, 탭, 접기, 작업 행동에 모두 접근할 수 있다. 완료 전환 후 입력 초점과 선택 텍스트를 보존한다.
- 스크린리더: 단계 변경·완료만 적절히 알리고 토큰·카운트마다 전체 대화를 반복 낭독하지 않는다. 색상만으로 상태를 구분하지 않는다.

### 8.1 복구와 새 시도의 구분

| 상황 | 사용자에게 제공할 행동 | 요청·시도 규칙 |
|---|---|---|
| 접수 응답 유실·처리 여부 불명 | 접수 상태 확인 | 기존 키와 동일 payload 유지, 부재 또는 종료가 확인되기 전 새 생성 금지 |
| 서버가 재시도를 허용한 동일 요청 실패 | 같은 요청 재시도 | 서버의 retry 행동 사용, 새 실행 식별자가 오면 원래 요청과 연결하고 실행 횟수 표시 |
| 정리 과정에서 첨부 snapshot 변경·기존 키 재사용 불가 | 새 시도로 다시 만들기 | 기존 시도 종료·비접수 확인 후 새 snapshot·키 사용, 안전한 이어하기로 표현하지 않음 |
| 파일·프롬프트·설정 변경 | 요청 수정 → 변경한 요청으로 만들기 | 변경 전후를 구분한 새 attempt, 이전 시도와 연결, 새 키 사용 |
| 생성 성공 후 결과 조회 실패 | PPT 다시 불러오기 | 기존 결과 조회만 실행 |
| 파일 내보내기 실패 | 파일 내보내기 재시도 | 기존 PPT 유지, 서버가 허용한 내보내기 행동만 실행 |

- 기존 업로드 오류 처리의 `pendingPresentationId` 재발급을 무조건 제거하거나 모든 오류에 그대로 적용하지 않는다. 접수 여부 불명·같은 payload 재시도·snapshot 변경을 분류한 뒤 해당 규칙을 적용한다.
- ‘요청 수정’은 실패·취소된 시도 아래의 인라인 편집 영역으로 진입한다. 최초 프롬프트·설정과 유효한 첨부를 채우고 만료되거나 사라진 첨부만 재선택하도록 한다. 완성 후 보낼 수정 초안과 이 편집값은 별도 상태다.
- 입력을 고치는 동안 새 작업은 실행하지 않는다. ‘변경한 요청으로 만들기’에서 새 스냅샷과 키를 확정하고 이전 메시지·실패 기록은 변경하지 않는다.
- 이전 시도가 아직 실행 중이거나 접수 여부가 불명확하면 변경 내용을 초안으로만 보관한다. 기존 시도가 종료된 후에만 새 시도를 제출한다.
- 새 attempt가 같은 서버 presentation 안에서 실행되면 같은 서버 타임라인을 유지한다. 기존 API가 별도 presentation을 생성해야 한다면 이전 기록을 합성 메시지로 복사하지 않고 서버가 권한 확인 가능한 이전/다음 시도 관계를 제공해야 한다. 이 관계가 없으면 현재 탭의 연결만 가능하므로 영속적인 ‘같은 대화’ 완료 조건은 미충족으로 표시한다.
- 입력이 바뀐 새 시도는 새로운 사용자 요청과 진행 영역을 갖는다. 동일 요청의 서버 재시도는 기존 진행 영역 안에서 시도 횟수와 이력으로 구분한다.

## 9. 적용 순서

1. 상태 소유권·요청/메시지 연결·재시도 분류를 먼저 연결한다. 기존 서버 계약의 부족한 연결 필드만 확인하고 보완한다.
2. 탐색과 수정 대상, 상태 전이·허용 행동을 구현한다. mode별 실제 진행 데이터와 최소 화면을 연결한다.
3. 기존 공통 provider와 준비/편집 화면에 업로드·구성 검토·완료 결과를 연결한다. 직접 링크·새로고침·이탈 복구가 동일 상태를 사용하게 한다.
4. 공통 채팅 스타일과 5개 와이어프레임을 적용하고 완료 후 PPT 배치, 가용 폭 기반 반응형, 스크롤·초점을 마무리한다.

기능 단위로 연결이 끝난 진입점에서만 기존 진행 팝업을 제거한다. 일부 모드만 지원되는 중간 상태를 전체 완료로 보고하지 않는다.

## 10. 구현 완료 판정 기준

다음은 향후 구현의 인수 조건이며, 이 문서 작성 시 실행한 테스트가 아니다. 구현 검증은 저장소 지침에 따라 해당 변경을 직접 다루는 가장 작은 검증 하나를 선택한다.

- 유효한 업로드 요청 후 진행 팝업·중간 개요 화면 없이 전체 대화가 보인다.
- 초기 요청·첨부·설정이 한 번만 표시되고, 접수 전후에 내용이 바뀌지 않는다.
- 실제 진행 이벤트가 한 진행 영역에 반영되며, 없는 단계·퍼센트·요약을 생성하지 않는다.
- 사용자 선택이 필요한 경우 같은 화면에서 처리하며 중복 제출하지 않는다.
- 서버 성공과 결과 준비가 확인된 뒤 왼쪽 PPT를 한 번만 연다.
- 전환 시 대화 기록, 입력 초안, 첨부, 스크롤 위치와 키보드 초점이 보존된다.
- 생성 중 작성한 초안이 완료 직후 자동 전송되지 않는다.
- 슬라이드 보기와 명시적인 수정 대상 선택을 구분하고, 전송 후 대상이 변하지 않는다.
- 재접속·중복 이벤트·응답 유실이 중복 생성이나 중복 메시지로 이어지지 않는다.
- 생성 실패, 결과 조회 실패, 내보내기 실패가 각각 올바른 재시도 행동을 제공한다.
- 기존 생성 품질·원문 보존·내보내기 모드별 동작은 UI 변경으로 우회되지 않는다.
- 좁은 화면에서 PPT와 채팅에 모두 접근하고, 키보드만으로 주요 작업을 수행할 수 있다.
- 파일 3개 이상·긴 최초 요청·긴 목차·오류 표시와 입력창이 공존해도 주 행동에 접근할 수 있다.
- 단순 썸네일 탐색은 수정 대상을 바꾸지 않고, 선택 대상이 삭제되면 범위 재선택 전 전송되지 않는다.
- 동일 요청 재시도와 조건 변경 새 시도가 구분되며, 이전 시도의 늦은 이벤트가 현재 결과를 덮어쓰지 않는다.
- 접수 유실·snapshot 교체·서버 첫 메시지 연결이 확인되고, 임시 메시지와 영속 메시지가 중복되지 않는다.
- 채팅 드래그만으로 탭 모드로 바뀌지 않으며, 컨테이너 폭 변화 후 선호 폭과 읽기 위치를 복원한다.
- 작업·계정 이동 시 초안·첨부가 섞이지 않으며, 저장 불가 환경에서도 기존 서버 작업을 중복 실행하지 않는다.
- §5.1의 취소/완료 경합, 완료 중복, 수정 요청 직렬화가 같은 상태 모델을 따른다.

## 12. v2 구현 반영과 계약 경계 — 과거 검증 이력

- 전체 대화 준비 화면을 업로드·개요 단계에 적용하고, 기존 workspace 채팅을 생성 중 전체 폭과 완료 후 오른쪽 패널에서 사용한다. 필수 원문 처리 선택과 개요 편집은 인라인으로 처리한다.
- 공통 레이아웃의 `GenerationWorkspaceProvider`가 자료별 초안·대기 첨부·대상·복구 정보를 보관한다. 기존 페이지와 렌더러의 생존 범위를 보존하기 위해 하나의 거대한 `GenerationWorkspaceHost` 대신 공통 provider와 준비/편집 화면 간 상태·초점 전달 방식을 사용한다.
- 서버가 확정한 결과와 렌더링 자료를 바탕으로 PPT 영역을 열고, 이후 수정 중에는 이전 결과를 유지한다. 가용 폭 기준 분할·탭 전환, 키보드/포인터 폭 조절, 모바일 목록과 명시적 수정 대상 선택을 연결한다.
- 계정 식별자가 있는 경우 sessionStorage로 초안과 접수 확인 정보를 분리 보관한다. 접수 확인은 저장된 동일 요청·키를 사용하며 로그아웃·인증 만료 시 해당 대화 캐시를 삭제한다. 사용자 ID가 없거나 저장소가 차단되면 메모리 범위로 동작한다.
- 최초 요청과 서버 메시지는 서버가 소유권·작업·대화 귀속을 확인한 메시지 ID로 연결한다. 새 응답에서 연결 ID가 명시적으로 없으면 서버 타임라인만 표시하고, 연결 필드가 없는 과거 응답에만 기존 보완 방식을 사용한다.
- 입력을 바꾼 새 시도는 별도 presentation과 새로운 입력·요청 키를 사용한다. 서버가 이전 자료의 소유권과 작업 종료를 확인한 후 불변 요청에 이전 시도 ID를 기록하고, 접근 가능한 이전·다음 시도의 대화 링크를 조회 시 제공한다. 이전 메시지를 새 타임라인에 복사하지 않는다. 요청 수정 화면은 원래 요청과 기본 설정을 불러오며, 첨부는 재첨부하고 스타일 등 생성 설정을 확인한 후 제출한다.
- 초안의 첨부 상태는 서버 자산 조회로 다시 확인하며, 읽던 메시지 ID·상대 위치와 픽셀 위치를 함께 보관해 같은 계정의 화면 복원에 사용한다.
- 다른 탭의 capability 변경과 focus/pageshow·화면 복귀 시 서버 권한을 재조회한다. 탭 메시지만으로 권한을 부여하지 않으며, 이전 요청을 취소해 늦은 응답을 차단한다. 재조회 중에는 대화를 유지하고, 명령 권한 해제·복구 시 초안을 보존한다. 인증 만료·로그아웃 시 진행 중 조회를 취소하고 권한을 해제한다.
- 검증: 이전 구현 단계의 편집 화면 9개·업로드 3개·채팅 33개 컴포넌트 테스트, 렌더링·이미지 무결성 4개, 생성 정보·시도 관계의 소유권/재접수 10개, 대화 메시지 연결 5개가 통과했다(중복 실행 제외 64개). 결함 수정 후 실행 중인 `http://localhost:5000`에서 `workspaceChatFirstRoute` 브라우저 테스트 11개 전부 통과(35초, 실패 0). 탭 간 권한 해제·복구와 초안 유지, 최초 요청 복원, 이벤트 재연결, 생성 완료 후 편집, Fidelity 내보내기 요청과 오래된 산출물 표시, 승인/취소·경합·재접수, 생성 중 전체 채팅 및 완료 후 컨테이너 폭 기반 분할/탭 전환을 검증했다. 브라우저 API 응답과 산출물은 fixture이며, 실제 모델 호출·PPTX 생성·실데이터 결과 표시는 이번 검증에 포함하지 않았다.

## 13. v3.1 ChatGPT형 대화 UI 상세 설계

### 13.1 적용 범위와 우선순위

2026-09-23 사용자 제공 화면과 후속 설계 검토를 기준으로 대화의 시각적 위계와 조작 방식을 개정한다. 기존 생성·수정·내보내기 파이프라인과 서버 작업 계약을 유지한다. §1~10과 이 절이 현행 명세이며 §11~12는 개정·구현 이력이다. 대화 폭·취소 위치·수정 대상·공통 상태 보관 지시를 본문에도 통합했다. 색조·행간·장식 간격은 실제 화면 확인 시 조정할 수 있다. 대화 최대 폭 800px, 채팅 최소/최대 360/600px, PPT 최소 600px, 구분선 8px, 분할 경계 968px와 폭 계산식은 인수 기준으로 고정하며 변경 시 본문과 경계 조건을 함께 개정한다.

화면의 기본 단위는 사용자 요청과 그에 따른 AI 응답이다. 진행 상태·결과·복구 행동은 해당 응답 안에 배치한다. 기존 작업 이벤트를 모두 개별 대화 카드로 늘어놓지 않으며, 영속 이벤트와 메시지의 관계는 그대로 보존한다. 디자인과 상호작용을 적용하는 범위이며 ChatGPT 브랜드·아이콘을 복제하지 않는다.

### 13.2 화면 위계와 시각 규격

| 요소 | v3 명세 |
|---|---|
| 앱 헤더 | 자료 제목 한 줄, 길면 말줄임과 전체 제목 접근 제공. 필요한 문서 메뉴만 유지 |
| 대화 헤더 | 별도 큰 `Slides Workbench`, 설명문, 상시 `Live` 표시 제거. 연결 이상이나 필요한 상태만 작은 문구로 표시 |
| 전체 대화 | 흰 배경, 최대 폭 800px, 중앙 정렬. 본문과 입력창 폭·정렬선 동일 |
| 사용자 메시지 | 오른쪽 정렬, 연한 회색 배경, 둥근 모서리 20px, 본문보다 좁은 최대 폭 85% |
| AI 응답 | 왼쪽 정렬, 카드 테두리·큰 배경 없이 본문으로 표시. 진행과 결과는 응답 내부에 배치 |
| 글자 | 기본 15~16px, 줄 높이 1.6 전후. 상태·파일 부가 정보는 12~13px, 충분한 대비 유지 |
| 간격 | 사용자 요청과 AI 응답 묶음 사이 28~32px. 응답 내부 상태 간격 8~12px |
| 첨부 | 파일 아이콘·이름·크기 중심의 작은 카드. 원시 MIME은 상세 정보로 이동. 파일 접근 권한에 맞춰 열기·다운로드 제공 |

| 시스템 안내 | 중립적인 한 줄 안내. 과거 요청 원문이 없으면 `첨부 파일로 시작한 요청입니다`로 표시하고 원문을 추측하지 않음 |

상단의 전역 `요청 수정해서 다시 만들기` 버튼은 해당 실패 응답의 행동으로 이동한다. 문서 전체에 영향이 있는 다른 작업과 혼동하지 않도록 이전 시도에 연결한다. 원본 요청 기록은 수정하지 않는다.

### 13.3 화면 상태와 전환

| 상태 | 화면과 입력 | 전환 조건 |
|---|---|---|
| 생성 전 | 기존 업로드 요청·첨부·디자인 선택 | 사용자가 만들기를 제출하면 동일 요청 스냅샷을 첫 메시지로 표시 |
| 접수·분석·생성 | 전체 대화, 한 개의 AI 진행 응답, 하단 초안 작성 가능 | 서버가 확인한 단계와 완료 수만 갱신 |
| 필수 선택·구성 확인 | 동일 응답에 인라인 선택 영역 | 확인 행동을 제출해야 다음 단계 진행 |
| 완료·결과 조회 중 | 완료 메시지와 PPT 불러오는 상태 | 서버 완료와 조회 가능한 결과가 함께 확인돼야 분할 |
| 결과 표시 가능 | 왼쪽 PPT·오른쪽 동일 대화, 입력 전송 가능 | 컨테이너 폭에 따라 분할 또는 PPT/채팅 탭 |
| 수정 작업 중 | 이미 열린 PPT는 유지, 채팅 응답에서 수정 진행 | 검증된 새 리비전을 조회한 뒤 PPT 갱신 |
| 생성 실패·취소 | 현재 대화와 초안 유지, 해당 응답에 상태·허용 행동 | 결과가 없으면 전체 채팅 유지; 이전 결과가 있으면 계속 표시 |
| 연결 끊김 | 마지막 서버 상태와 연결 안내 유지 | 상태를 다시 조회하며 시간 경과만으로 실패·완료를 추정하지 않음 |

좁은 화면에서는 §2.3 탭 규칙을 적용한다. 완료 시 입력 중이거나 과거 메시지를 읽는 사용자를 강제로 PPT 탭으로 이동시키지 않고 `PPT 보기`를 제공한다. 분할 전환으로 conversation, 메시지 ID, 첨부, 초안, 선택 대상, 읽기 위치를 초기화하지 않는다.

### 13.4 진행 응답과 결과 행동

- 최초 AI 응답은 현재 수행 중인 일을 한 문장으로 설명한다. 그 아래 완료된 단계에는 체크, 실행 중 단계에는 움직임 표시와 텍스트를 제공한다.
- 현재 단계와 실제 완료 장수를 우선한다. 예: `슬라이드 생성 중 · 3/30장`. 장수는 이벤트가 정의한 완료 단위를 사용하며, 수신된 초안 수를 검증 완료 장수로 바꾸지 않는다.
- 완료 수나 전체 수가 없는 단계는 `자료 분석 중`, `슬라이드 배치 중`처럼 단계만 표시한다. 임의 퍼센트·예상 잔여 시간·가짜 스트리밍 문장을 만들지 않는다.
- 한 operation의 이벤트는 같은 진행 영역을 갱신한다. 상세 이벤트는 `작업 내역 보기` 안에서 펼친다. 다른 작업과 서버 재시도의 식별은 유지한다.
- 생성 성공 후 과정은 접을 수 있고 완료 결과를 남긴다. 결과 메시지의 `전체 화면`은 준비된 PPT를 연다.
- `PPTX 다운로드`는 현재 리비전에 사용 가능한 파일이 있을 때 다운로드한다. 아직 없으면 `PPTX 만들기`로 기존 내보내기를 요청하고, 내보내기 진행·완료 상태를 표시한다. 만료·이전 리비전 파일을 최신 결과처럼 제공하지 않는다.
- 실패·취소 후 움직임과 실시간 따라가기 표시는 종료한다. 마지막 퍼센트는 주요 영역에서 제거하고 필요하면 작업 상세에 이력으로 보관한다. 연결 상태와 작업 실행 상태를 하나의 `Live` 배지로 합치지 않는다.

### 13.4.1 장기 작업과 연결 상태 안내

기존 §3.2.1의 60초 기준을 유지하고 다음과 같이 해석한다. 아래 명칭은 표현 데이터의 의미이며 서버에 같은 이름의 새 필드를 반드시 추가한다는 뜻은 아니다.

| 값 | 갱신 근거 | 갱신하면 안 되는 경우 |
|---|---|---|
| 마지막 서버 확인 | 현재 작업 상태를 확인한 정상 조회 또는 해당 작업을 확인하는 서버 이벤트 | 브라우저 타이머, 단순 소켓 연결, 다른 작업 이벤트 |
| 마지막 진행 변화 | 현재 시도의 단계·완료 수·서버의 구체적인 작업 진척 변경 | 동일 상태 재조회, 중복 이벤트, 연결 heartbeat |
| 연결 가용성 | 기존 transport의 연결·조회 성공/실패와 freshness 기준 | UI가 자체적으로 만든 성공 상태 |

- 현재 작업의 실행 상태가 최신으로 확인되지만 60초 동안 실제 진척이 없으면 `서버에서 실행 상태를 확인했어요. 진행 변화는 아직 없습니다.`와 두 시각을 구분해 표시한다. 이를 정상 처리 속도나 곧 완료된다는 보장으로 표현하지 않는다.
- 최근 서버 상태를 확인할 수 없으면 `연결을 확인하고 있어요`와 마지막 확인 시각을 표시한다. 오래된 실행 상태만 보고 계속 처리 중이라고 단정하지 않는다.
- 대기열·사용자 선택 대기는 해당 상태의 안내를 우선한다. 장기 실행 안내로 필수 선택 버튼을 가리지 않는다.
- 60초는 안내를 시작하는 기준이며 작업 timeout이 아니다. 경과 시간만으로 실패·취소·자동 재시도·추가 모델 호출을 실행하지 않는다.
- `상태 확인`은 기존 조회 경로를 사용한다. 조회 중 연속 클릭을 막고 별도 polling loop를 만들지 않는다. 동일 상태 응답은 마지막 진행 변화 시각을 초기화하지 않는다.
- 이전 시도의 늦은 이벤트와 중복 이벤트는 현재 시각·진행 수를 변경하지 않는다. 진행 시각을 복구할 근거가 없으면 `확인 정보 없음`으로 표시한다.
- terminal 상태에서는 안내 타이머를 종료한다. 안내 진입 때 한 번 알리고 매초 스크린리더 알림을 반복하지 않는다.

### 13.5 오류와 복구

오류는 해당 AI 응답에서 한국어 설명 한 번과 가능한 다음 행동으로 제시한다. 영문 일반 오류, 붉은 박스, 노란 안내를 중복해서 표시하지 않는다. 실패 아이콘과 텍스트를 함께 사용하고 색상에만 의존하지 않는다.

서버가 안전하게 제공한 오류 코드·대상 페이지가 있을 때만 구체적인 원인을 안내한다. 원인을 알 수 없으면 `생성을 완료하지 못했어요. 작업 상세를 확인하거나 요청을 수정해 주세요.`로 표시한다. 이번 화면의 일반 오류만 보고 배치 부족이나 특정 페이지 실패라고 추정하지 않는다. 요청 ID·오류 코드·마지막 확인 시간은 접힌 상세 정보에 보관하고 원문 로그·stack trace는 노출하지 않는다.

| 서버가 확인한 상황 | 행동 |
|---|---|
| 동일 작업 재시도 허용 | `다시 시도` — 서버가 제공한 행동 사용 |
| 재시도 불가·입력 변경 필요 | `요청 수정` — 인라인 편집 후 명시적 제출로 새 시도 생성 |
| 취소 지원·실행 중 | 입력창 전송 자리의 `생성 중지` — 응답에는 중복 버튼을 두지 않음. 접수 후 `중지 요청 중`, 서버 확정 후 `중지됨` |
| 완료했으나 결과 조회 실패 | `PPT 다시 불러오기` — 생성 요청을 중복 제출하지 않음 |
| 내보내기 실패 | 허용된 `내보내기 다시 시도` — 생성된 PPT는 유지 |
| 접수 결과 불명·연결 끊김 | `상태 확인` — 기존 요청 식별자로 조회 |

행동 가용성은 서버 capability와 현재 권한을 기준으로 한다. 비재시도 오류에 `다시 시도`를 표시하거나 네트워크 요청 취소를 서버 작업 취소 완료로 취급하지 않는다.

### 13.6 고정 입력창과 수정 대상

- 입력창은 채팅 패널 하단의 고정 영역이며 메시지 스크롤 밖에 둔다. 모서리 24px, 얇은 테두리, 왼쪽 아래 첨부 버튼, 오른쪽 아래 전송 버튼으로 구성한다.
- 입력 높이는 내용에 따라 최대 약 180px까지 확장하고 그 이후에만 입력 내부를 스크롤한다. 전송 가능 여부는 텍스트 입력만으로 판정하지 않고 §13.6.1의 요청·첨부·권한·대상 조건을 함께 사용한다.
- 생성 중에는 초안을 작성할 수 있지만 자동 전송·예약 실행은 하지 않는다. 취소가 지원되면 전송 위치에 `생성 중지`를 표시하고, 지원하지 않으면 전송 불가 사유를 한 줄로 안내한다. 중지해도 초안을 지우지 않는다.
- Enter 전송, Shift+Enter 줄바꿈을 사용하되 한글 IME 조합 중 Enter는 제출하지 않는다. 중지 버튼이 있어도 Enter로 취소하지 않는다.
- 수정 대상은 입력창 위에 `대상 선택`, `전체 발표자료`, `3페이지 수정 ×` 중 하나로 표시한다. 최초 수정 진입은 미선택이며, 사용자가 범위를 명시적으로 선택한다. 탐색 중인 페이지가 바뀌어도 고정한 수정 대상은 바뀌지 않는다.
- ×로 대상을 제거하면 미선택으로 돌아가 전송을 막는다. 전체 자료로 자동 확대하지 않으며 초안·첨부는 유지한다. 대상 슬라이드가 삭제됐거나 서버가 확인할 수 없을 때도 같은 규칙을 적용한다. 선택된 범위는 전송 버튼 주변과 전송된 메시지에서 확인할 수 있어야 한다.
- 실패 요청의 인라인 수정 값과 다음 수정 요청의 초안은 분리한다. 로그인 만료나 권한 변경 시 기존 보관·삭제 규칙을 유지한다.

### 13.6.1 전송 가능 조건과 첨부 상태

전송 버튼은 다음 조건을 모두 만족할 때 활성화한다.

1. 공백을 제외한 텍스트 또는 현재 요청에 제출 가능한 첨부가 하나 이상 있다.
2. 포함할 모든 첨부가 서버의 해당 명령에서 요구하는 준비 상태와 접근 권한을 갖춘다.
3. 명령 권한이 유효하고 실행 중·접수 여부 불명·승인 대기 등 기존 서버 정책상 전송 금지 상태가 아니다.
4. 수정 요청은 사용자가 선택한 유효한 대상과 기준 리비전이 있다. 최초 생성에는 이 조건을 적용하지 않는다.
5. 해당 명령이 입력 조합을 지원한다. 최초 생성의 첨부 단독 요청은 기존 지원을 유지한다. 수정 명령이 지시문을 요구하면 첨부를 보존하고 지시문 작성을 안내하며, UI가 수정 의도를 만들어 실행하지 않는다.

| 입력·첨부 상태 | 전송·복구 동작 |
|---|---|
| 텍스트 없음 + 첨부 없음 | 비활성화 |
| 유효한 텍스트만 있음 | 나머지 권한·작업·대상 조건 충족 시 전송 |
| 준비된 첨부만 있음 | 해당 명령의 첨부 단독 지원과 나머지 조건 충족 시 전송 |
| 포함된 첨부 중 업로드·필수 분석 대기 있음 | 전송 대기와 해당 파일 상태 표시 |
| 포함된 첨부 중 실패·만료·접근 불가 있음 | 전송 차단, 파일별 재첨부·제거 등 허용 행동 표시 |
| 정상 첨부와 실패 첨부가 함께 있음 | 실패 파일을 몰래 제외하지 않음. 복구하거나 사용자가 제거한 뒤 다시 판정 |

전송 시점에도 첨부와 대상을 서버가 재검증한다. 권한·파일 상태가 바뀌면 초안을 보존하고 복구한다. 같은 전송 동작의 연속 클릭·Enter에는 기존 idempotency와 제출 잠금을 적용한다. 명시적 첨부 제거는 현재 초안에서만 제외하며 과거 메시지의 파일이나 서버 자산을 삭제하지 않는다.

중지 버튼은 입력 내용 유무와 독립적으로 현재 생성·수정 operation의 취소 capability에 연결한다. 생성·수정 취소와 내보내기 취소를 섞지 않으며, 내보내기 작업의 취소는 해당 응답에서 제공한다. 중지 요청 후 완료가 먼저 확정되면 서버 최종 결과를 따르고 입력 초안을 유지한다.

### 13.7 스크롤·반응형·접근성

- 채팅 패널 안에서는 메시지 목록 하나만 세로 스크롤 소유자가 된다. 상위 작업 컨테이너는 높이를 제한하고 별도의 문서 스크롤을 만들지 않는다. 입력창이 목록 위를 덮지 않도록 별도 행으로 배치한다.
- PPT 썸네일, 긴 입력 내용, 전역 탐색 메뉴의 필요한 스크롤은 독립 기능이다. 이를 없애기 위해 전체 앱을 한 스크롤로 합치지 않는다.
- 하단에 있거나 사용자가 새 메시지를 보낸 경우 하단을 따라간다. 과거 기록을 읽는 경우 위치를 유지하고 `새 메시지 ↓`를 표시한다. 단계 이벤트마다 강제로 하단으로 이동하지 않는다.
- `AI 따라가기`가 필요한 경우 PPT 패널의 활성 수정 상태에서만 표시한다. 메시지 자동 스크롤과 PPT 페이지 추적은 별도 상태이며 terminal 이벤트에서 PPT 추적을 해제한다.
- 최소 360px 화면에서도 가로 넘침이 없어야 한다. 터치 주요 버튼은 약 44px 조작 영역을 확보하고 화면 키보드·safe area를 반영한다.
- 입력·버튼·접기·분할 조절에 명확한 접근성 이름을 제공한다. 상태 변경은 `aria-live`로 간결하게 알리고 전체 메시지를 반복 낭독하지 않는다. 애니메이션은 움직임 줄이기 설정을 따른다.
- 분할 조절 손잡이는 키보드 초점을 받을 수 있는 세로 separator이며 조절 대상과 현재·최소·최대 폭을 노출한다. 좌우 방향키는 경계를 16px씩, Shift와 함께 누르면 48px씩 이동시키고 Home/End는 허용 최소/최대 채팅 폭으로 이동한다. 실제 폭은 §2.3 범위를 넘지 않는다. 손잡이가 사라지는 탭 전환에서는 새로 표시된 영역의 해당 탭 버튼으로 초점을 복원하고, 입력창에서 작업 중이었다면 입력 초점을 유지한다.

기존 공통 provider와 서버 이벤트·명령 경로를 재사용한다. 아래는 직접 연결된 구현 대상이며 새로운 병렬 채팅 시스템을 만들지 않는다.

| 대상 | 변경 책임 |
|---|---|
| `generation-workspace/GenerationPageFrame.tsx`, `GenerationPreparation.tsx` | 전체 대화 폭·높이·스크롤과 초기 진행 화면 정렬 |
| `presentation/workspace/WorkspaceChatPanel.tsx` | 현재 화면의 Workbench 헤더, 작업 응답 구성, terminal 표시와 자동 스크롤 |

| 기존 operation 표시 컴포넌트 | 진행·실패·복구 행동을 해당 AI 응답에 통합; 기존 reducer와 서버 행동 유지 |
| `WorkspaceConversationComposer.tsx`, `WorkspaceComposer.tsx` | 고정 입력창, 수정 대상, 초안·첨부·전송·중지와 IME |

| 기존 번역 리소스 | 상태·오류·버튼 문구; API 오류 코드와 식별자는 변경하지 않음 |

1. 현재 활성 UI 경로를 확인하고 중첩 카드·스크롤·헤더를 정리한다.
2. 메시지·첨부·설정·입력창을 공통 규격으로 맞춘다.
3. 실제 이벤트 기반 진행·종료·오류·복구 표시를 연결한다.
4. 결과 표시 조건과 분할·탭 전환, 초안·읽기 위치 보존을 연결한다.
5. 변경 계층의 가장 좁은 기존 검사로 확인한다. 전체 E2E·빌드·실제 모델 생성은 이 문서만으로 자동 실행 범위에 추가하지 않는다.

### 13.8.1 공통 표현 계층과 기존 제어 경계

준비 화면, Workbench, canonical 경로는 메시지 외형·첨부 목록·설정 요약·진행 응답·오류 행동·입력창 표현과 디자인 토큰을 공유한다. 실제 컴포넌트 이름은 기존 구조를 기준으로 구현 시 정하되, 경로마다 별도의 색상·간격·버튼 상태 규칙을 복제하지 않는다.

| 책임 | 담당 경계 |
|---|---|
| 인증·권한·서버 상태·이벤트 순서·조회·재시도·명령 제출 | 각 경로의 기존 transport/controller/hook |
| 메시지·operation·리비전·허용 행동을 화면 데이터로 변환 | 각 경로의 얇은 adapter와 공통 순수 표현 함수 |
| 말풍선·진행·오류·첨부·입력·대상 표시 | 공통 표시 컴포넌트, 데이터와 callback을 전달받음 |
| 초안·대상·읽기 위치·분할 폭의 지속성 | 기존 provider와 작업별 저장 계약 |
| PPT 내용·썸네일·직접 편집 | 기존 뷰어와 리비전 갱신 경로 |

공통 표현 데이터에는 안정적인 메시지/operation 식별자, 역할, 실제 단계와 완료 수, 두 확인 시각, 파일 준비 상태, 명시적 수정 대상, 실행 가능한 행동과 비활성화 이유를 포함한다. 원문 메시지·서버 작업 데이터를 새 저장소에 복제하지 않는다. 서버에 없는 단계나 권한을 adapter가 추정하지 않는다.

표시 컴포넌트는 생성 API를 직접 호출하거나 별도 SSE·polling·재시도 루프를 만들지 않는다. 행동 callback은 operation ID와 현재 허용 행동에 연결하고 서버가 실행 시 다시 확인한다. 표시 데이터가 캐시돼 있어도 오래된 권한을 실행 권한으로 사용하지 않는다.

### 13.8.2 렌더링과 성능 경계

- PPT 뷰어는 문서·리비전·명시적 페이지 선택이 바뀔 때 필요한 부분을 갱신한다. 채팅 입력, heartbeat, 진행 카운트 변경으로 뷰어를 재마운트하거나 전체 슬라이드 이미지를 다시 조회하지 않는다.
- 메시지에는 안정적인 키를 사용한다. 한 operation의 진행 이벤트는 해당 응답만 갱신하며 전체 대화 Markdown 재해석·파일 미리보기 재생성을 유발하지 않도록 경계를 둔다.
- 표시용 연속 카운트 갱신은 짧게 묶을 수 있지만 terminal 상태·필수 선택·권한 변경은 지연시키지 않는다. 이벤트 수신·저장·순서 검증은 생략하지 않는다.
- 긴 기록은 기존 페이지 단위 조회를 재사용한다. 새 가상 스크롤 도입은 실제 병목이 확인될 때만 검토하고, 도입 시 메시지 앵커와 초점·접근성 보존을 별도로 확인한다.
- 파일 이름·크기·상태는 가벼운 메타데이터로 표시한다. 스크롤 밖 첨부의 원본 이미지·문서 미리보기를 매 렌더마다 디코딩하지 않는다.
- 성능이 개선됐다는 주장은 실제 측정 후에만 한다. §13.9.1의 조건은 후속 구현의 검토 기준이며 측정이나 전체 성능 검사를 이미 실행했다는 뜻이 아니다.

### 13.9 v3.1 인수 기준과 검증 범위

설계 문서 작성 단계에서는 제품 코드·서버를 변경하거나 테스트를 실행하지 않는다. 다음 항목은 후속 구현의 완료 기준이다.

- 생성 중 전체 대화와 완료 후 오른쪽 대화가 같은 메시지·입력창 규격을 사용한다.
- 대화 목록 중첩 스크롤이 없고, 마지막 응답이 고정 입력창에 가려지지 않는다.
- 긴 한글 요청·긴 파일명·여러 첨부가 가로 넘침 없이 표시되고, 누락된 과거 프롬프트를 창작하지 않는다.
- 한 작업의 진행은 같은 응답에서 갱신되고 실제 단계·완료 수만 표시한다.
- 실패 화면에는 오류 설명 한 번과 허용된 복구 행동만 남고, 진행 애니메이션·`따라가는 중`은 종료된다.
- 완료 후 결과 조회 실패를 생성 실패로 표시하지 않으며, 오래된 PPTX를 최신 파일로 다운로드시키지 않는다.
- 분할·탭·경로 전환 후 최초 요청, 초안, 첨부, 수정 대상, 읽기 위치가 유지된다.
- IME 조합 Enter, 중복 제출, 중지 경합, 접수 여부 불명, 권한 만료는 기존 서버 계약을 보존한다.
- 후속 화면 검토 대상은 생성 중·실패·완료 분할·좁은 탭 화면이다. 이 검토를 수행하기 전에는 v3 시각 품질 통과라고 보고하지 않는다.

| 한글 IME Enter·중복 제출·중지/완료 경합 | 조합 확정은 전송하지 않음, 명령 중복 없음, 서버 최종 상태와 초안 유지 |
| 키보드·스크린리더: 손잡이·탭·접기 및 완료/분할 전환 | separator 방향·대상·현재/최소/최대 폭 확인, 방향키·Home/End의 한계 준수, 가시적 초점, 숨겨진 요소에 초점 잔류 없음, 입력 초점 탈취와 반복 상태 낭독 없음 |
| 긴 기록 표본: 메시지 200개·첨부 메타데이터 20개·진행 이벤트 100개 | 작업 응답이 이벤트 수만큼 늘어나지 않음, 입력·초점 유실 없음, PPT 뷰어 재마운트·슬라이드 재조회 없음 |
| 동일 fixture를 준비/Workbench/canonical 표현에 공급 | 메시지·첨부·진행·오류·버튼 가용성의 표현 일치, 별도 서버 실행 루프 없음 |

숫자는 경계 조건과 재현용 fixture 기준이다. 표 전체를 자동 전체 테스트 실행 지시로 해석하지 않는다. 후속 구현은 변경 계층에 직접 대응하는 기존의 좁은 검사부터 선택하고, 시각 확인은 위 대표 화면을 대상으로 범위를 명시해 수행한다. 시간 기반 성능을 보고할 경우 같은 장비·브라우저·fixture에서 입력부터 다음 표시까지의 지연과 스크롤 장시간 정지를 비교해 측정 조건을 함께 기록한다. 현재 설계에는 측정하지 않은 응답 시간 보장을 넣지 않는다.

§12의 과거 테스트 결과와 이번 설계 반영을 구분한다. v3.1 구현·검증 결과는 실제 수행 후 별도 기록한다.

## 15. v3.1 구현과 검증 기록 — 2026-09-23

공통 메시지·입력 프레임을 준비/작업공간/canonical 화면에 적용했다. 800px 대화 정렬, 단일 메시지 스크롤, 고정 입력창, 사용자 말풍선과 본문형 AI 응답을 사용한다. 결과가 준비되면 가용 폭 968px 이상에서 기본 65:35 분할, 그 미만에서 탭을 적용한다. 사용자 조절 폭, 키보드 조절, 초점과 초안을 보존한다.

수정 대상은 미선택으로 시작하고 해제 후 전송을 막는다. 기존 편집 명령은 텍스트를 요구하므로 첨부 단독 편집 전송을 허용하지 않는다. 실패 첨부를 임의로 누락하지 않으며 접수 여부 불명 상태에서는 새 요청·첨부를 막고 초안을 유지한다. 입력창 중지는 정확한 operation에 연결하며 서버가 취소를 확정할 때까지 완료로 표시하지 않는다.

진행은 실제 단계·완료 수를 사용하며 heartbeat의 퍼센트 변경으로 진척 시각을 갱신하지 않는다. 중복·오래된 이벤트와 부분 조회에서 반환되지 않은 작업은 확인 시각을 갱신하지 않는다. 한국어 오류는 한 번 표시하고 완료 후 결과·행동은 유지하며 제작 이력만 접는다. 기존 `progress` 이벤트 별칭도 유지한다.

실제 서버의 기존 실패 문서를 1440px 및 390px 폭에서 확인했다. Workbench/정상 Live 헤더와 중복 영문 오류가 없으며 입력창은 화면 아래에 유지된다. 두 폭 모두 body 폭이 viewport와 같고 body 높이가 1000px viewport를 넘지 않았다. 생성 중·완료 분할의 실제 서버 시각 확인과 성능 측정은 이 확인에 포함되지 않는다.

요청 수정의 현재 범위는 대화 내 문구 편집 후 명시적인 `수정 내용으로 설정 확인`이다. 기존 업로드 화면에서 이전 설정을 복원하고 필요한 원본을 다시 첨부한 뒤 재생성을 제출한다. 파일·템플릿·admission 검증을 소유한 기존 제출 경로를 재사용하며, 대화 내 편집만으로 새 생성 API를 호출하지 않는다. §13.5의 완전한 인라인 재생성 제출은 아직 구현 범위에 포함되지 않는다.
