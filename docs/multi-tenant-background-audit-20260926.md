# Background multi-tenant readiness audit (2026-09-26)

Scope: code paths started outside an HTTP request on `origin/main` at `6d7fa3e41`. A background controller may deliberately scan all tenants to discover work; that is **safe** only when subsequent work uses a row-bound identity or a global maintenance invariant. **Fails closed** means a missing tenant prevents a tenant-bound operation. **Cross-tenant risk** means the code has no tenant discriminator when the same owner UUID appears in two tenants. The latter is a readiness finding, not proof of a production incident. The chat-memory finding below was exercised with a real persisted operation and a second-tenant delivery.

Central rule: `database_owner_scope.py:92-113,176-216` adds ORM owner criteria to owner-scoped models and tenant criteria only to `PublicOperationAdmission`, `PublicArtifact`, and `PublicExportIdentity`. Owner-only models and direct SQL writes are not made tenant-isolated by setting a tenant context. `workspace_operation_runner.py:4351-4362` restores the tenant from admission, captured payload, or legacy carrier through `workspace_operation_principal.py:68-95`; conflicting sources fail. A missing source leaves only the owner. The runner's claim, heartbeat, and recovery are controller-wide by design.

## Before enabling multi-tenant in production

1. Persist a tenant on every owner-only durable authority that can be reached by a shared external subject: workspace operations/assets/conversations, source-locked jobs, webhook subscriptions, and legacy generation jobs. Migrate existing rows with a verified tenant or quarantine them; never assign a default tenant.
2. Disable legacy unlinked generation dispatch and tenantless authenticated outbox rows until their submission and recovery paths enforce the tenant. Keep authored code frozen; make its tenant contract a separate approved change.
3. Test with **one owner UUID in two tenants** against command execution, asset processing, webhook delivery, source-locked recovery, account deletion, export, and cleanup. Assert the second tenant's rows and external storage objects are invisible or the operation fails closed.
4. Verify PostgreSQL RLS and SQLite test behavior for direct `UPDATE`/`DELETE` statements as well as ORM reads. Confirm tenant-bearing artifact references and storage keys match their admission rows.
