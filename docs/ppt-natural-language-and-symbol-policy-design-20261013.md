# PPT 문구 자연화와 기호 사용 정책 설계

신규 PPT의 제목, 본문, 표 설명과 도표 설명을 구체적인 실무 문장으로 작성한다. 단어 나열용 가운데 점, 긴 대시와 장식 기호를 제한하고, 추상적인 효과와 반복되는 문장 틀을 줄인다. 문구 편집은 화면 배치 전에 수행하며, 원문 사실과 편집형 표·차트 데이터를 보존한다.

상태: 설계 완료, 구현 전. 이 문서 추가로 실행 중인 서버나 PPT 생성 로직이 바뀌지는 않는다.

## 요구사항과 적용 범위

사용자가 확정한 요구는 다음과 같다.

- `중복·누락·참조` 같은 단어 구분용 기호와 길게 늘인 대시를 PPT 생성에서 사용하지 않는다.
- 앞서 나열한 불릿, 화살표 문자, 세로 구분선, 슬래시, 장식 표시, 체크 표시와 반복 문장부호의 장식적 사용도 제한한다.
- 제목과 본문을 사람이 작성한 업무 문서처럼 구체적이고 자연스럽게 다듬는다.
- 추상적인 효과, 슬로건형 제목, 반복되는 대비와 세 가지 장점 나열을 줄인다.
- 제목, 본문, 표, 주의사항은 각각의 역할에 맞는 문체를 사용한다.
- 원문 사실을 보존하고, 문구를 확정한 뒤 화면을 생성한다.
- 품질을 우선하고 그다음으로 속도를 고려한다.

아래의 호출 배치, 저장 방식, 판정 기준과 적용 순서는 구현 설계안이다. 새 Deck IR, 좌표 계획, 레이아웃 배정표, 별도 생성 엔진은 만들지 않는다. LLM의 화면 구성 자유도는 유지한다.

정책은 신규 요청의 생성 문구에 기본 적용한다. 기존 문서와 고정된 요청의 재개에는 자동 소급하지 않는다. 기존 문서를 바꾸려면 정상 페이지 재작성 명령을 통해 별도 후보를 만들고 반영한다.

## 현재 코드와 연결 위치

| 현재 경로 | 확인한 동작 | 연결할 책임 |
|---|---|---|
| `utils/llm_calls/generate_content_brief.py` | 원문을 `ContentBrief`로 정리 | 초기에 자연스러운 문체를 사용하고 사실 근거 유지 |
| `models/content_brief_model.py` | 제목, 개요, 섹션, 주장, 수치 자료 보관 | 기존 사실과 편집 가능한 문구 구분 |
| `utils/llm_calls/generate_presentation_outlines.py` | 페이지별 내용을 생성 | 제목과 문구 작성 기준 적용, 편집할 초안 공급 |
| `services/generation_core/authoring/author_slide_svg.py` | 원문과 사용자 지시를 받아 문구와 SVG를 함께 작성 | 확정 문구로 자유롭게 구성하고 새 문구 추가 제한 |
| `services/generation_core/authoring/author_slide_prompt.py` | HTML 작성 입력을 조립 | SVG와 같은 문구 정책 연결 |
| `services/generation_core/authoring/author_source_svg_layout.py` | 원본 사실과 표·차트·이미지의 보존을 요구 | 원문 보존 계약 우선, 생성된 보충 문구만 적용 |
| `services/generation_core/authoring/author_raster_svg_layout.py` | 원본 텍스트를 고정하고 기하·스타일만 작성 | 원본 및 OCR 문구의 자동 변경 금지 |
| `services/svg_page_remake.py` | 작성 후보와 텍스트를 보존하는 로컬 후보 구분 | 문구 수정은 작성 경로 사용, 로컬 편집 계약 유지 |
| `services/authored_content_brief_checkpoint.py` | 같은 입력의 brief와 시간 예산 재사용 | 정책 변경을 입력 해시에 포함하고 재사용 범위 보존 |
| `services/generation_core/drivers/svg/quality.py` 및 `services/svg_page_publication.py` | 후보 검토와 측정 결과에 연결된 게시 | 문구 검사 결과를 기존 후보 검증에 연결 |

경로는 `servers/fastapi/` 기준이다. 현재 `ContentBrief`는 슬라이드가 생기기 전의 지식 정리 결과다. 이를 최종 슬라이드 문구 검토 완료로 간주하지 않는다.

## 기호 정책

### 새로 작성하는 문구에서 제한할 표현

| 분류 | 대상 | 작성 방법 |
|---|---|---|
| 가운데 점 | `·`, `ㆍ`, `‧`, `∙`, `⋅` | 단어 나열은 쉼표, 관계는 자연스러운 문장 |
| 장식 불릿 | `•`, `●`, `◦`, `▪`, `‣` | 문장 안 구분에 사용하지 않음. 목록은 줄바꿈, 들여쓰기 또는 의미 있는 번호 사용 |
| 긴 대시 | `–`, `—`, `―` | 쉼표, 괄호 또는 별도 문장으로 작성 |
| 화살표 문자 | `→`, `⇒`, `➜`, `➔`, `⟶` 및 장식용 `->`, `=>` | 순서는 문장이나 번호로 설명. 실제 도식의 연결선은 보존 |
| 세로 구분선 | `|`, `｜`, `│` | 단어 구분은 쉼표 또는 별도 행 |
| 연결용 슬래시 | `/`, `／`, 장식용 역슬래시 | 병렬 단어는 쉼표, 선택 관계는 실제 의미에 맞게 설명 |
| 강조 장식 | `※`, `★`, `☆`, `◆`, `◇`, `▶` | 내용과 제목 자체로 중요도 표현 |
| 체크 표시 | `✓`, `✔`, `☑`, `✅` | 확인 상태를 단어로 작성하거나 실제 상태를 나타내는 기존 도형 사용 |
| 반복 문장부호 | 장식용 `…`, `...`, `!!`, `??`, `--` | 완결된 문장과 필요한 문장부호 사용 |
| 부가 장식 | 의미 없이 붙인 이모지와 그대로 노출된 Markdown 강조 기호 | 문구에서 제거하고 기존 서체·강조 기능 사용 |

원문을 설명하기 위한 정책 예시의 기호와 내부 Markdown 목록 문법은 PPT의 표시 문구가 아니다. 생성 프롬프트 전체나 원문 저장 문자열을 대상으로 삭제하지 않는다.

### 의미가 있는 기호와 원문 보호

다음은 단어 장식과 구분한다.

- 음수, 차감, 날짜, 범위, 수식, 분수와 단위.
- URL, 이메일, 파일 경로, 코드, API 값, 제품명, 공식 명칭과 고유 식별자.
- 원문 인용, 법적 문구, 수치 표의 셀, 차트의 범주와 시리즈 이름.
- 사용자 또는 원본이 지정한 실제 체크리스트 상태와 목록 순서.
- 원본 이미지 및 스크린샷 안의 글자, 실제 도형 연결선과 화살촉.

새로 쓰는 범위 표현은 `10~20%` 또는 `10%에서 20%`처럼 표현할 수 있다. 보존해야 하는 원문 `10–20%`를 문자열 치환으로 바꾸지는 않는다. ASCII 하이픈 `-`도 날짜·음수·제품명에서 유지한다.

기호가 보호된 값에 속하는지 불명확하면 원문을 유지한다. 이때 정책 적용 범위를 기록하고 검사 완료로 숨기지 않는다. 원문 인용을 가장해 생성 문구 전체를 예외 처리할 수 없으며, 보호 대상은 실제 원본 구간이나 기존 데이터 식별자로 연결한다.

## 자연스러운 문구 작성 기준

### 구체적인 대상과 행동

독자가 필요한 대상, 동작, 조건과 결과를 쓴다. 수치나 기대 효과는 원문에 있을 때만 사용한다. 없는 원인, 기능, 주체, 비교 대상이나 성과를 더해 문장을 구체화하지 않는다.

`혁신`, `최적화`, `시너지`, `극대화`, `고객 중심`, `지속 가능한 성장`, `새로운 패러다임`은 검토 대상이다. 실제 업무나 기술을 설명하는 근거가 있으면 유지한다. 단어 출현만으로 금지하지 않는다.

### 제목은 슬라이드의 역할에 맞춤

구성도에는 구성 대상을, 비교표에는 비교 기준을, 정책 설명에는 적용 조건을 쓴다. 결론을 제시할 근거가 있는 페이지는 구체적인 결론을 제목으로 사용할 수 있다. 모든 제목을 성과 주장이나 동사형 문장으로 통일하지 않는다.

| 기존 문구 | 편집 예시 | 보존할 의미 |
|---|---|---|
| 핵심은 업무 관계를 유지하되, 저장 목적별 경계를 먼저 고정하는 것입니다. | 업무 관계는 유지하고, 먼저 저장 영역의 경계를 목적별로 정합니다. | 업무 관계 유지, 목적별 경계 설정, 선행 순서 |
| 하나의 플랫폼 정책으로 경험·업무·운영 기반을 연결 | 고객 화면과 업무, 운영에 같은 플랫폼 정책을 적용합니다. | 해당 페이지 원문에 있는 세 적용 대상과 공통 정책 |
| 중복·누락·참조 | 중복, 누락, 참조 | 세 항목과 원래 순서 |
| 적용을 검토할 예정입니다. | 적용 여부를 검토할 계획입니다. | 미확정 상태와 예정 시점 |

편집 예시는 원문이 해당 의미를 뒷받침할 때만 적용한다. 제목을 바꾸면서 조건을 지우거나 전체 슬라이드의 주장을 강화하지 않는다.

### 반복되는 문장 틀 검사

- `핵심은`, `중요한 것은`, `궁극적으로`로 시작하는 반복.
- `단순히 A를 넘어 B`, `A가 아니라 B` 같은 근거 없는 대비.
- `이를 통해 ...을 실현합니다`로 끝나는 상투적인 결론.
- 모든 페이지에서 세 가지 장점을 만드는 나열.
- 행동 없이 `강화`, `확보`, `제고`, `도모`를 이어 붙이는 문장.
- 제목이나 바로 앞 문장을 다시 풀어 쓰는 불필요한 본문.

반복과 추상성은 문맥을 검토하는 신호다. 인과관계를 설명하는 `이를 통해`나 실제로 세 항목인 원문은 유지할 수 있다. 같은 대상을 표현할 때 용어를 일관되게 사용하되, 반복을 피하려고 전문 용어를 임의로 동의어로 바꾸지 않는다.

### 영역별 문체

| 영역 | 작성 기준 |
|---|---|
| 제목 | 대상과 요점이 드러나는 짧은 표현 |
| 본문 | 필요한 주체와 행동이 분명한 문장, 조건과 예외 유지 |
| 표 | 같은 기준의 간결한 항목, 단위·수치·범주 값 보존 |
| 도표 설명 | 자료에서 확인되는 변화와 비교 범위를 설명 |
| 주의사항 | 적용 조건, 금지 사항, 미확정 상태를 명확히 작성 |

문장형 본문에는 완결된 서술을 사용한다. 제목과 표의 짧은 항목을 억지로 문장으로 늘이지 않는다. 설명을 짧게 만드는 과정에서 필수 근거나 관계를 삭제하거나 글자 크기를 줄이는 문제로 넘기지 않는다.

문체는 요청의 언어, 청중과 말투를 따른다. 기본 한국어는 명확한 업무 문체이며, 다른 언어나 친근한 말투를 지정한 요청까지 동일한 종결형으로 바꾸지 않는다. 사실·원문 보존 계약과 사용자의 명시적인 표현 요구를 먼저 적용하고, 문구 정책을 다음으로 적용한다. 선택 템플릿의 장식 문구가 이 우선순위를 뒤집지 않는다.

## 작성과 편집 처리 순서

1. 원문과 수치·고유명사·조건·인용 등 보호 대상을 기존 자료 처리 경로에서 확보한다.
2. 기존 brief와 개요 작성에 공통 문구 정책을 전달해 첫 초안부터 해당 기준으로 작성한다.
3. 기존 콘텐츠 작성 호출에서 제목과 본문을 작성하고 스스로 다듬는다. 문서의 용어와 문체를 공유하되 역할별 표현은 구분한다.
4. 원문을 그대로 보여 주는 경로와 사실을 바탕으로 새 문장을 쓰는 경로를 구분한다. 원문 그대로 재구성하는 작업은 표현과 기호까지 보존한다.
5. LLM이 화면을 자유롭게 작성한다. 배치에 맞춰 문구를 줄일 때도 수치, 조건, 부정, 범위와 순서를 유지하며 임의 삭제로 공간을 맞추지 않는다.
6. 최종 표시 문구를 기존 후보 검사에서 확인한다. 장식 기호는 제한된 기존 수정 경로로 처리하고, 문체 신호는 독립적인 사실 검토 통과와 구분해 기록한다. 수정된 후보는 기존 측정과 검토를 다시 따른다.

별도 편집이 필요한 경우 입력은 실제 문구, 역할, 원문 근거와 보호 범위다. 별도 편집기는 수정이 필요한 기존 문구 식별자와 대체 문구만 반환해야 한다. 기본 구현은 기존 작성 호출과 기존 후보 수정 경로를 사용하므로, 별도 편집 호출이나 독립적인 편집 승인 영수증이 생겼다고 표시하지 않는다.

원문과 외부 문서는 편집 자료로만 전달한다. 원문 안의 프롬프트 변경 지시를 실행하거나 보호 범위·정책을 해제하는 근거로 사용하지 않는다. 자료와 정책 지시는 기존의 신뢰 경계를 유지한다.

기존 개요 결과에 최종 표시 문구가 실제로 들어 있는 경우 그 결과를 사용한다. 개요가 자료 요약에 그치는 경우 기존 페이지 작성 입력을 만들 때 편집할 문구를 먼저 준비한다. 요약 내용을 검토했다는 이유로 이후 작성된 문구까지 승인된 것으로 간주하지 않는다.

편집 결과는 기존 콘텐츠 필드에 반영하고 편집 이력만 별도 메타데이터로 남긴다. 도형 목록, 페이지 장면 그래프나 배치 계획으로 확장하지 않는다. 최종 문구와 원문 근거는 구별해서 보관한다.

## 내용 보존과 후보 검증

### 변경 허용과 제한

문장 순서와 표현은 사실·조건·예외·관계를 유지하는 범위에서 다듬는다. 긍정과 부정, 검토와 확정, 예상과 실적, 일부와 전체, 승인 전과 승인 후를 서로 바꾸지 않는다. 없는 주체를 추가하거나 단어가 짧아진 것을 의미 보존으로 인정하지 않는다.

수치·단위·기간·고유명사와 native 데이터의 검사는 기존 근거와 실제 원문을 기준으로 한다. LLM이 작성한 `의미를 보존했다`는 자체 설명만으로 통과시키지 않는다. 의미 보존을 확인할 수 없는 수정은 채택하지 않고 해당 원문 문구를 유지한다.

기호 삭제와 문체 개선은 서로 별도로 검사한다. 기호가 없다고 자연스러운 문장으로 판정하지 않으며, 짧아졌다고 품질이 좋아졌다고 판정하지 않는다.

### 화면 작성에서 문구 유지

화면 작성은 보호된 원문을 임의로 슬로건으로 바꾸거나 근거 없는 요약 문장을 추가하지 않는다. 새로 쓴 brief·개요 문장은 원문 사실, 수치, 관계, 조건, 부정과 순서를 유지하며 자연스럽게 다듬을 수 있다. 원문 그대로 재구성하는 경로는 줄바꿈과 텍스트 실행 단위 분할만 허용하며, 숫자, 문자, 조건이나 항목을 바꿀 수 없다. 별도 승인된 문구가 있는 경우 해당 승인 계약을 먼저 따른다.

SVG는 `<text>`와 `<tspan>`의 실제 문자열을 검사한다. HTML은 실제 표시 텍스트와 목록 마커를 검사한다. 원문, 프롬프트, SVG 속성, 경로 데이터나 비표시 메타데이터에 정규식 치환을 수행하지 않는다. 보이지 않는 텍스트로 필수 문구를 숨기고 표면상 문구 검사를 통과할 수 없다.

기본 템플릿이 장식 구분자를 자동으로 붙이는 경우 LLM 응답만 고쳐서는 해결되지 않는다. 생성 콘텐츠와 서버가 추가하는 문구를 각각 추적해 신규 표시 문구에 같은 정책을 적용한다. 브랜드명이나 사용자가 지정한 원본 문구는 보호한다.

새로 만드는 이미지에는 의미 없는 장식 문구를 넣지 않도록 자산 작성 지침에 연결한다. 본문은 가능하면 편집 가능한 텍스트로 유지한다. 원본 이미지 글자에는 삭제 검사를 적용하지 않는다. OCR만으로 모든 이미지 문구를 검증했다고 주장하지 않는다.

### 품질 판정

| 항목 | 검사 방법 | 처리 |
|---|---|---|
| 새 문구의 장식 기호 | 보호 범위를 구분한 문자와 실제 표시 검사 | 확정 전에 해당 구간 수정 |
| 수치·고유명사·조건 변경 | 원문·보호 값·기존 데이터 계약 대조 | 수정 후보 거절 |
| native 셀·차트 데이터 변경 | 원본 데이터와 최종 객체 대조 | 후보 또는 내보내기 거절 |
| 보호 원문 누락·재작성 | 실제 원문과 기존 source/native 계약 대조 | 화면 후보 수정 필요 |
| 추상성·상투성·반복 | 편집 검토와 기존 문서 품질 검토 | 근거가 있는 해당 구간만 편집 |
| 줄바꿈·잘림·겹침 | 기존 측정과 최종 렌더 검사 | 기존 화면 수정 경로 사용 |

사람 작성 확률이나 AI 탐지 점수를 성공 지표로 사용하지 않는다. 생성 문구 규칙 준수, 내용 보존과 실제 결과 비교를 평가한다. 사용자 `vision_qa=false` 설정을 바꿔 활성화하지 않는다.

## 속도와 호출 계획

기본 경로는 기존 작성 호출에 작성과 자기 편집 지침을 함께 전달하며, 별도 제공자 호출은 0회다. 별도 편집이 필요한 실제 문구만 기존 승인된 수정 예산 안에서 처리한다. brief나 작성 프롬프트에 지침을 전달했다는 이유로 독립적인 문구 검토가 완료됐다고 간주하지 않는다.

큰 문서를 무조건 한 요청에 넣지 않는다. 전체 문서의 용어·문체 기준을 공유하면서 실제 입력 용량과 최악의 수정 출력량을 기준으로 묶음을 나눈다. 80페이지를 항상 한 호출로 처리하거나 고정된 2페이지·5페이지 상한을 모든 경로에 적용하지 않는다. 출력은 변경 문구만 반환한다.

호출 수는 입장 단계에서 예정된 편집 묶음과 기존 작성·수정 요청을 합쳐 등록한다. 전역 호출 한도를 임의로 높이지 않는다. 실제 사용하는 제공자의 요청 형식과 입력 제한으로 검사하며, 측정하지 않은 토큰 수를 정확한 값처럼 기록하지 않는다.

동일한 원문, 문구 입력, 정책 버전, 보호 범위, 모델과 지시의 편집 결과는 재사용한다. 기존 고정 예산과 작업 기한을 연장하지 않는다. 해당 묶음만 바뀌면 그 묶음만 무효화한다. 실패했다고 문서 전체의 편집을 다시 실행하지 않는다.

기본 편집 자동 재시도는 0회로 설계한다. 수정이 필요한 명확한 문구 위반은 기존 승인된 작성·수정 예산 안에서 처리한다. 알려진 전송 전 입력 오류는 새 입력 검사로 해결하고, 결과 불명 호출은 자동 반복하거나 완료로 바꾸지 않는다.

문체 편집이 불가능해도 원문 보호와 기호 지침을 기존 작성 호출에 전달한다. 완료 상태는 `편집 검토 미완료`로 구분한다. 자연스러운 표현의 주관적 평가만으로 무제한 생성 재시도를 만들지 않는다. 명확한 내용 훼손이나 필수 문구 누락은 기존 사실 검증에서 계속 차단한다.

성능 비교는 같은 자료·페이지 수·모델·캔버스에서 수행한다. 전체 시간, 편집 시간, 호출 수, 재사용 수, 출력 오류, 화면 재생성 수를 분리한다. 추가 편집 시간이 줄바꿈 재작성 감소로 상쇄되는지는 구현 후 실제 결과로 확인한다.

## 저장과 재개 계약

설계상 정책 식별자는 `ppt-writing-policy/v1`이며, 표시 언어와 기호·문구 규칙 버전을 함께 고정한다. 정책은 기존 요청 및 콘텐츠 체크포인트의 버전 있는 메타데이터로 보관한다. 저장을 우회하는 `exclude=True` 필드나 프로세스 메모리만으로 유지하지 않는다.

기본 구현은 정책을 durable 요청, brief 입력 해시와 페이지 작성 입력 해시에 연결하고 실제 작성 프롬프트 영수증을 사용한다. 표시 검사에는 사유별 개수와 보호된 기호 개수를 기록하며 원문을 저장하지 않는다. 별도 편집기를 도입할 때만 편집 입력·보호 범위·수정 문구 식별자·승인 출력 해시를 추가한다. 원문 및 기존 콘텐츠를 덮어쓰지 않으며 정책이 바뀌면 해당 입력의 체크포인트 재사용을 막는다.

새 DB 테이블이나 별도 작업 큐를 기본 전제로 하지 않는다. 기존 개요·콘텐츠 체크포인트 payload에 편집 결과를 함께 보관할 수 있는지 먼저 확인한다. 기존 저장 스키마로 보장할 수 없다면 구현 범위와 필요한 스키마 변경을 별도로 명시하고 검토한다.

작성 입력과 영수증에 정책을 연결하되, 시각 스타일 YAML을 문구 편집 결과 저장소로 사용하지 않는다. 작성 프롬프트 해시에는 실제 사용한 문구와 정책을 포함한다. 데이터 스키마, 프롬프트, 파서, 검사와 재개가 같은 정책 버전을 사용해야 한다.

검토 오류는 원문을 로그에 남기지 않고 허용된 사유 코드와 수정 구간 수로 기록한다. `검토하지 않음`, `검토 완료`, `보호 원문 유지`, `편집 일부 미확정`과 `호출 결과 불명`을 서로 구분한다. 원문 보호 때문에 남은 기호를 생성 문구 규칙 위반 0건에 포함해 성공으로 숨기지 않는다.

## 생성 경로별 적용

| 입력과 동작 | 적용 |
|---|---|
| 프롬프트로 새 PPT 생성 | 제목·본문·설명에 기본 적용 |
| 문서·PDF·표 자료에서 새 문구 작성 | 새로 쓴 문구를 편집하고 원문 인용·수치·조건 보호 |
| PPTX 원문 그대로 재구성 | 원본 사실 텍스트·셀·차트 범주 보존, 신규 보충 문구만 적용 |
| 이미지·스크린샷 원본 보존 | 이미지와 OCR 고정 문구 유지, 신규 제목·설명만 적용 |
| SVG 자유 작성 및 HTML 작성 | 같은 정책 사용, 기존 구성 자유도 유지 |
| 템플릿 데이터 생성 | 편집 가능한 생성 필드와 서버 추가 문구에 적용, 데이터 값 보존 |
| 페이지 다시 만들기 | 새 작성 후보에 명시적 정책 적용, 정상 revision과 게시 경로 사용 |
| 로컬 SVG 배치 수정 | 기존 텍스트 보존 계약 유지, 문체 변경에 사용하지 않음 |
| 기존 작업 재개·내보내기 | 원래 고정 정책 사용, 새 기본값 자동 소급 금지 |

원본 표현까지 고치라는 명시적 요청이 있으면 원문 보존 작업에 지시만 추가하지 않는다. 수정할 수 있는 구간을 선언한 정상 재작성 후보로 처리하고, 원본과 표시 문구를 구분해 검증한다. native 데이터와 승인·금지 조건은 계속 보존한다.

## 구현 순서와 변경 책임

1. 공통 문구·기호 정책, 보호 범위와 검사 결과 계약을 정의한다.
2. 기존 brief·개요 작성에 자기 편집 지침을 연결하고, 요청 및 콘텐츠 체크포인트에 동일한 정책 버전을 보존한다.
3. SVG·HTML·템플릿 작성 입력에 정책을 전달하고 원문 보존 경로에는 정확한 원문 보호를 적용한다.
4. 기존 후보 검증에 표시 문구 검사와 제한된 수정 힌트를 연결한다. 독립적인 사실 검증과 문체 신호의 결과를 구분한다.
5. 정상 신규 요청을 기본 활성화하되, 고정 요청의 재개는 이전 계약을 유지한다.

작은 공통 정책 모듈과 기존 프롬프트·콘텐츠 처리 연결을 먼저 구현한다. 완성 SVG를 정규식으로 후처리하는 기능, 폰트 축소, 템플릿 강제 교체나 전체 슬라이드 자동 재생성을 해결책으로 넣지 않는다. 사용자 설정과 기본값이 생기면 실제 선택 옵션과 기본 적용 값을 함께 맞춘다.

멀티 에이전트 구현은 공통 정책·내용 보존, 정책 저장·실제 호출 연결, 작성 프롬프트, 독립 코드 검토로 소유 범위를 나눈다. 입장·게시·Git 통합은 한 담당자가 수행한다. 결과 불명인 기존 제공자 작업은 반복하지 않는다.

## 검증과 완료 조건

통합된 구현에 직접 대응하는 가장 좁은 검증을 1회 선택한다. 구현 결과의 시각적 비교와 성능 측정은 사용자가 요청한 검증 범위로 실행한다. 정책 전달, 표시 문구 검사, 독립 사실 검토와 실제 사용자 품질 평가를 각각 구분해 보고한다.

향후 확인할 사례는 다음과 같다.

- 가운데 점과 긴 대시가 있는 일반 생성 문구는 자연스러운 표현으로 바뀐다.
- 음수, 날짜, 공식 명칭, URL, 원문 인용과 수식은 유지된다.
- 검토 예정, 미확정 수치, 승인 전 조건과 부정 표현이 확정·실적·허용으로 바뀌지 않는다.
- 실제 세 항목과 기술적인 `통합` 표현은 불필요하게 제거되지 않는다.
- 원본 보존·스크린샷 경로는 원문을 유지하고 적용 제외 근거를 기록한다.
- 작성 모델이 확정 문구를 바꾸거나 새 문구를 덧붙이면 이를 발견한다.
- 로컬 배치 수정은 문구 편집을 우회하지 못한다.
- 중단 후 재개가 같은 문구·정책을 재사용하고 호출을 중복하지 않는다.
- 큰 문서는 실제 입력·출력 용량과 승인 호출 계획 안에서 처리된다.
- 편집형 표·차트의 값과 범주가 최종 PPTX에도 동일하다.

기능 완료는 정상 웹 신규 요청에서 실제 정책이 고정되고, 생성된 표시 문구의 장식적 금지 기호가 없으며, 원문 사실과 native 데이터가 보존된 결과로 판정한다. 기존 12페이지 사례는 고정된 비교 자료의 사본으로 사용할 수 있다. 이전 문서를 자동 변경하거나 공급자 결과 불명인 최종 검토를 이 작업에서 재실행하지 않는다.

문구 품질은 같은 자료의 전후 제목·본문·표 설명을 비교해 판단한다. 목표는 명확한 대상과 행동, 원문 근거, 역할에 맞는 문체, 반복 감소다. 자연스러운 문장처럼 보이게 하기 위해 내용 정확도를 낮추지 않는다.
