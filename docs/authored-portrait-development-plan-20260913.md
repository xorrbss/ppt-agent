# 세로형 Authored 개발 실행 계획

기준: authored-portrait-generation-design-20260912.md v3. 상태: 실행 제안, 아직 에이전트 실행·제품 구현 전.

## 범위

기존 Authored 생성기와 저장·측정·렌더·출력 경로를 확장한다. 첫 대상은 default 스타일의 9:16이다. 가로 기본값과 기존 품질 기준을 유지한다. 회사 마스터/기타 스타일의 세로 지원, hybrid 공개 확대, A4, 생성 후 방향 전환은 제외한다. 개발 에이전트 모델 선택은 제품의 PPT 생성 provider/model 설정과 별개다.

## 역할과 모델

| 역할 | 난이도 | 권장 모델 / reasoning | 소유 범위와 납품물 |
| --- | --- | --- | --- |
| L 통합 리드 | 매우 높음 | gpt-5.6-sol / high | 공통 계약, 파일 소유권 표, 교차 변경 승인, 통합과 실행 검증 |
| A 요청·영속성 | 높음 | gpt-5.6-sol / high | 요청 정규화, staging 왕복, theme canvas 저장·재열기·복원·재생성 |
| B 생성·배치·품질 | 높음 | gpt-5.6-sol / high | 마스터 없는 canvas 해석, default 세로 배치, 기존 수용량/local-fit 연결, Python 캡처 |
| C 렌더·출력 | 매우 높음 | gpt-5.6-sol / high | TS viewport 계약, fidelity 번들 소유 소스, PPTX 치수와 raster PDF |
| D UI | 중간 | gpt-5.6-terra / medium | 방향 선택, 지원 조합 표시, 문서 캔버스 미리보기·썸네일 |
| R 독립 검토 | 높음 | gpt-5.6-sol / high | 작성자와 분리해 계약 손실·고정값·가로 회귀를 읽기 전용 검토 |
| E 증거 정리 | 낮음 | gpt-5.6-luna / medium | 리드가 제공한 검사 결과에서 파일·치수·작업 ID·미확인 사항 정리 |

모델 배정은 작업 위험에 따른 추천이며 해당 저장소에서 비교 측정한 성능 순위가 아니다. 일반 구현은 Sol 이하로 구성한다. 여러 경로의 충돌을 Sol로 해소하지 못할 때만 gpt-6-astra/high를 통합 진단 대안으로 고려한다. Luna에 스키마·수리 정책·export 치수 계약 결정을 맡기지 않는다. R/E는 항상 별도 상주시키지 않고 빈 슬롯에 순차 실행한다.

모델 참고: https://developers.openai.com/api/docs/models — 공식 설명의 복잡한 작업용 Sol, 균형형 Terra, 비용 중심 Luna 구분을 참고했다. reasoning과 역할 배치는 본 계획의 판단이다.

## 실행 순서와 통과 조건

### P0: 공통 계약과 파일 소유권 확정

L이 파일 수정 전 dirty 상태와 관련 AGENTS를 확인한다. A는 저장·복원 writer, C는 fidelity 번들 런타임의 실제 소유 소스, D는 실제 생성 폼의 위치를 읽기 전용으로 확인한다. B는 default 스타일 적용 진입점과 Python 캡처 호출자를 확인한다. 동시 실행은 L+A+B+C+D의 최대 5개다.

L은 반환 결과를 바탕으로 aspect_ratio 필드, canvas 직렬화 형태와 버전, safe_area 해석, 과거 기본값, 오류 응답, export 전달 인자, capability 응답 위치를 문서로 고정한다. 근거가 달라져 저장안 조정이 필요하면 기존 사용자 요구를 유지하면서 조정 근거를 남긴다. 이 단계에서 writer 이름을 추측해 구현을 시작하지 않는다.

P0 종료 조건은 모든 필수 층의 실제 파일과 소유자가 지정되고 공통 인터페이스가 합의되는 것이다. 공통 타입의 변경은 L이 소유하거나 A/C 중 한 명에게 명시적으로 위임한다.

### P1: 연결 가능한 구현 병렬 진행

A/B/C/D가 정해진 파일만 수정한다. 인터페이스에 맞춰 각자 구현하되 UI의 실제 세로 옵션 활성화는 마지막까지 보류한다. A는 저장·복원 무결성, B는 default 수직 구성과 기존 품질 정책, C는 viewport·페이지 크기·캐시 정합성, D는 선택값 왕복과 문서 비율 표시를 완료한다.

B가 요청 파일 변경이 필요하면 A에 요청하고 직접 함께 편집하지 않는다. export payload의 Python 측은 L이 A/B 중 한 명에게 지정하고 TS 소비자는 C가 소유한다. UI가 사용하는 TS 공통 렌더 타입은 C가 소유하며 D는 소비만 한다. 다른 소유 파일의 수정이 필요하면 리드에게 경로·이유를 알리고 소유권을 이관한다.

각 에이전트의 납품은 변경 파일 목록, 변경 계약, 좁은 검증 결과, 미해결 사항이다. 소스·패치·원문 로그·문서 본문을 사용자 화면에 출력하지 않는다.

### P2: 통합과 독립 검토

L이 계약 생산자/소비자 연결을 통합한다. R은 구현자 역할과 분리된 새 컨텍스트에서 읽기 전용 검토한다. 검토 대상은 비율 누락, theme 키 손실, 과거 가로 문서 호환, snapshot digest 우회, 캐시 혼용, PDF/PPTX 물리 크기, 미지원 조합의 조용한 fallback이다.

검토자가 직접 광범위하게 수정하지 않는다. 발견 사항은 소유자에게 반환하고 해당 수정으로 결과가 바뀌는 좁은 검증만 다시 수행한다. 검토 통과 전 UI 지원 목록을 활성화하지 않는다.

### P3: 실제 경로 수용 검증

실행과 서버 제어는 L 한 명만 수행한다. 기존 관리 스택·PostgreSQL·포트를 유지하고 필요한 서버만 재시작한다. provider/model 설정은 개발 모델 배정 때문에 바꾸지 않는다. 생성 테스트를 각 에이전트가 중복 실행하지 않는다.

동일한 간단한 내용의 5장(표지·본문·이미지·차트·마무리)으로 실제 세로 생성과 다운로드를 확인한다. 실제 durable operation과 PPTX/PDF 산출물을 연결한다. PPTX 페이지 크기와 PowerPoint readback, PDF 페이지 크기와 내용 잘림을 확인한다. 문서 재열기·페이지 재생성·내보내기에도 비율이 유지되어야 한다.

가로 호환은 해당 층의 기존 좁은 검증을 우선 사용한다. 가로 실제 생성 비교가 필요한 미해결 우려가 있으면 통합 수용 범위에서 한 번만 추가한다. fixture 성공을 실제 세로 생성 성공으로 보고하지 않는다. 산출물 증거가 없으면 완료를 선언하지 않는다.

## 작업별 최소 검증

| 담당 | 구현 후 선택할 좁은 검증 |
| --- | --- |
| A | 기존 요청 직렬화/복원 관련 테스트에서 세로 왕복·과거 기본값·theme 보존을 직접 다루는 최소 범위 |
| B | 기존 캔버스/수용량/local-fit 검사 중 변경된 치수 전달을 직접 확인하는 최소 범위 |
| C | 기존 renderer/export 계약 검사 중 viewport 또는 페이지 크기 변경을 직접 확인하는 최소 범위 |
| D | 기존 생성 설정/미리보기의 좁은 검사; 없으면 해당 변경을 직접 확인하는 실행 확인 |
| L | 통합 후 실제 세로 생성→PPTX/PDF 수용 시나리오 |

각 작업은 가장 작은 검사 하나를 고르고 테스트·린트·타입 검사·빌드를 묶어 실행하지 않는다. 검증만을 위한 새 테스트를 만들지 않는다. 전체 테스트·전체 빌드·성능 측정은 포함하지 않는다. 위 표는 예정 범위이며 아직 수행한 검증이 아니다.

## 협업 운영 규칙

- 최대 동시 실행 5개. 기본은 L+구현 4개, 검토 단계는 작업이 끝난 슬롯을 R/E로 교체한다.
- 현재 dirty 변경을 기준으로 시작 상태를 보존한다. worktree를 쓸 경우 필요한 미커밋 변경이 빠진 HEAD만 복제해 기준으로 삼지 않는다.
- 공유 checkout에서는 파일별 단일 writer를 유지한다. broad reset/clean, 전체 staging, 타 에이전트 변경 덮어쓰기를 금지한다.
- 모든 하위 에이전트에게 프로젝트 지침과 화면 출력 제한을 전달한다. 로컬 서버 재시작, DB 조작, 실제 provider 생성은 L만 수행한다.
- 설계/공통 계약 변경은 리드가 관리한다. 작업자가 독립적으로 필드명·기본값·지원 범위를 바꾸지 않는다.
- 완료 보고는 수정 범위·실행한 검증·남은 위험을 분리한다. 코드 완료와 실제 사용 가능 확인을 구분한다.

## 시작 지시 단위

각 에이전트에는 설계 v3, 본 계획, P0에서 작성한 소유 파일 목록, 입력·출력 계약, 좁은 완료 기준을 함께 전달한다. 첫 실행은 P0이며 구현 전체를 동시에 무제한 위임하지 않는다. 예상 소요 시간은 P0에서 실제 writer·번들 소스와 변경 규모가 확인된 뒤 산정한다.
