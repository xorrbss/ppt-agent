# PPT 생성 성능 개선 설계 검토

- 작성일: 2026-10-22
- 범위: 설계 작성과 정적 검토. 애플리케이션 개발과 운영 활성화는 실행하지 않았다.
- 설계: [생성 성능 개선 설계](generation-performance-repair-design-20261022.md), 개정 2
- 설계 SHA256: `5CCB62456DED58BEDE78ADA84E605CEDDD509EFF3C3787596C499F850F63B7FB`
- 설계 작성: Claude Code Opus 조정자, 입력 계약 Sonnet, 복구와 동시성 Opus, 검사와 관측 Sonnet.
- 독립 검토: Codex 품질 보존과 복구 안전 검토자, 성능과 구현 명확성 검토자. 발견된 계약을 Claude Code가 보완한 뒤 수정 부분만 재검토했다.

## 1. 결론

검토한 범위에서 남은 필수 설계 수정 P0/P1/P2는 없다. 다만 모든 작업과 운영 활성화가 무조건 허용된다는 뜻은 아니다.

- W0 사실 확인과 W1 입력 중복 제거, W2 실패 범위 축소는 설계된 범위에서 개발할 수 있다.
- W3 자동 재개는 기존 dispatcher와 lease 재획득 경로가 확인된 경우만 진행한다. 새 dispatcher 개발로 범위를 넓히지 않는다.
- W5는 실제 설정과 동시성 증거, 기존 회계와 cached-first 계약을 확인한 분기만 변경한다.
- W4 조기 QA는 이번 개발에서 제외한다. 기존 자동 검사와 전체 일관성 검사는 유지한다.
- 운영 활성화는 admission과 worker claim을 확실히 차단하고 drain할 기존 수단이 확인된 뒤에만 가능하다.
- 이 문서는 개발 완료, 시각 품질 개선, 생성 속도 개선을 입증하지 않는다.

## 4. 개발 전에 확인할 조건

### W0와 W5

- 과거 당시의 설정, operation manifest, prepare의 in-memory override, stage plan 존재와 lineage 분기를 구분한다.
- 기본 author=2가 실제 2병렬이었다고 가정하지 않는다. 관측 overlap=1도 capacity=1의 증거가 아니다.
- 필요한 조회는 지정 job과 operation의 작은 scalar 메타데이터로 한정한다. 원본 SVG, 큰 metrics, 전체 복구 계보의 해시를 재계산하지 않는다.
- 확인되지 않은 직렬 경로를 변경하지 않으며, 기존 provider 한도와 공정성 계약을 유지한다.

### W2와 W3

- 동결 이후 새 dispatch 승인 0을 확인한다. 이미 승인된 형제의 제한된 후속 repair는 유효 lease, 예산, 시도 한도 안에서만 허용한다.
- fail_stage 이후 형제 checkpoint commit, 진행 표시, 늦은 결과 처리가 설계와 맞는지 구현 후 좁게 확인한다.
- 품질 소진 페이지가 하나라도 있으면 자동 재개하지 않는다.
- UNKNOWN 자동 재구매, 시도 횟수 리셋, 종료된 operation 되살리기, old fence 재사용은 금지한다.
- 기존 자동 재개 dispatcher가 없으면 W3 자동 경로를 보류한다.

### 운영 활성화

admission과 claim을 차단할 수단이 없으면 배포를 보류한다. 사용자가 적은 시간대라는 이유로 이 조건을 대신하지 않는다. 개발은 live worker가 읽지 않는 격리된 작업 공간에서 진행한다.

## 5. 품질과 속도에 관한 판단 한계

- 원문, 숫자, rich run, 표 병합, 관계, 페이지 수와 자유로운 전체 SVG 구성을 보존하는 계약을 검토했다.
- 실제 출력물의 디자인 품질과 편집성을 새로 평가하지 않았다.
- 100페이지 생성의 11,096초는 실행 9,264.4초, 재개 사이 공백 1,709.2초, 큐 122.4초로 나뉜다. 실행 시간을 전부 provider 대기로 취급하지 않는다.
- 평균 응답 155.7초와 입력 70,308토큰은 완료된 author 8건의 표본이다.
- 마지막 실행의 후행 약 895초는 QA, 두 페이지 수정과 발행을 합한 시간이다.
- 준비된 자산을 이용한 PPTX 내보내기 124.5초를 생성 성능 개선의 근거로 쓰지 않는다.
- 다음 정상 웹 생성의 자연 기록으로 필요한 관측값을 얻은 뒤에만 성능 효과를 판단한다. 별도의 100페이지 반복 생성 실험은 추가하지 않는다.

## 6. 이번에 실제로 수행한 확인

- Claude Code 설계자 3명의 문서를 통합했다.
- Codex 두 검토자가 설계와 직접 연결된 코드, 기존 테스트 접점을 읽었다.
- 알려진 원인과 미확인 값, 이전에 해결된 export와 교착 문제를 구분했다.
- 수정 부분만 다시 검토했으며, 최종 검토에서 남은 필수 문서 수정은 발견하지 못했다.
- 테스트, 벤치마크, 추가 PPT 생성, 내보내기, DB 조회, 서버 재시작은 실행하지 않았다.
- 작성과 수정 대상은 설계와 검토 문서 및 비공개 조정 기록이다. 애플리케이션 소스는 변경하지 않았다.
